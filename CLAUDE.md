# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Slopdaddy generates narrated AITAH/Reddit-story videos with burned-in captions over a background clip. Piper/Kokoro TTS (client-side ONNX) for narration and a pluggable set of AI providers for story generation (see "Story-generation providers" below) always run in-browser. Rendering and caption-sync transcription both have two tiers: `server.js` shells out to the user's own installed native `ffmpeg`/`whisper` when present and capable (see "Native rendering backend" and "Caption-sync cascade" below) — falling back to ffmpeg.wasm / an in-browser estimate otherwise. No bundler, no framework either way.

**Two branches, two purposes**: `main` is where active development happens, heading toward a standalone local app (see "Standalone app" below). `web` is a frozen-ish snapshot kept as the zero-install "click a link" browser-only version — that's what the deployed GitHub Pages site (https://youraveragecow.github.io/Slopdaddy/) builds from, gated by `.github/workflows/pages.yml`'s `workflow_run` filter on `web`'s own `Tests` runs, not `main`'s. Backport pure-logic fixes/features to `web` when practical (cherry-pick or manual port); native-only features (this whole file's "Native rendering backend"/"Caption-sync cascade"/"Standalone app" sections) don't apply there, since `web`'s `server.js` stays as plain static-file serving.

## Commands

```bash
node server.js              # local dev server at http://localhost:8123 (needed for COOP/COEP headers — opening index.html via file:// breaks isolation)
npm start                    # (main branch only) launches the standalone Electron app — same UI/backend, real app window instead of a browser tab
node --test web/lib/*.test.js   # run all tests (Node's built-in test runner, zero dependencies)
node --test web/lib/foo.test.js # run a single test file
node -c web/app.js           # syntax-check a file (no linter configured — this is the closest thing)

# Dev/diagnostic tooling (main only) — see scripts/smoke-test.js
SLOPDADDY_PORT=8199 node server.js   # run a second instance without quitting a live Electron app first
SLOPDADDY_DEBUG=1 node server.js     # log real ffmpeg/whisper spawn args + per-request status/timing
npm run smoke                        # scripted round-trip check against /render, /transcribe, cache endpoints — exits non-zero on failure
npm run free-port                    # kill whatever's holding SLOPDADDY_PORT (default 8123) — mac/linux only
```

`web/` itself has no build step, no bundler, no lint config — everything there is served as-is, and `server.js`'s render/transcribe backends shell out to native `ffmpeg`/`whisper` rather than adding npm dependencies to bundle them. `main`'s `package.json`/`package-lock.json`/`node_modules/` exist only for `electron` (the standalone app wrapper); `web/` stays dependency-free regardless. Double-clicking `Open AITAH Creator Web.command` runs `node run.js`, which starts `server.js` and opens the browser for you — independent of the Electron app.

Tests run automatically on push/PR via `.github/workflows/test.yml` (on both `main` and `web` pushes). `.github/workflows/pages.yml` (the GitHub Pages deploy) is gated on `web`'s Tests runs specifically: it triggers via `workflow_run`, not `push` directly, and only proceeds `if` that run succeeded (or on manual `workflow_dispatch`). A red test run on `web` blocks deployment.

## Versioning

`main`'s app version is `web/app.js`'s `const VERSION = N` (shown as the `v${VERSION}` badge in the UI, mirrored in `package.json`'s `"version"` as `"N.0.0"`). Bump `VERSION` by 1 — and `package.json`'s version to match — with every commit that ships a user-visible change on `main` (a new feature, a real bug fix, anything that changes what the running app does). Check the current `VERSION` against how many real releases have landed since the last bump before shipping, in case it's fallen behind.

## Architecture

### Native rendering backend (`server.js`), with automatic WASM fallback

`server.js` was originally pure static file serving. It now also exposes `POST /render` (plus `GET /render-capability` and an SSE `GET /render-progress/:id` for progress), which shells out to the user's own `ffmpeg` via `child_process` instead of ffmpeg.wasm — real native rendering is faster and doesn't hang the way the WASM multi-thread core occasionally does. It reuses `web/lib/ffmpeg-filters.js`'s pure filter-graph builders directly via `require()` — only the exec mechanism and file I/O differ from `ffmpeg-worker.js`'s WASM path, not the actual ffmpeg invocation.

`checkFfmpeg()` in `server.js` doesn't just check that `ffmpeg` exists — captions are burned in via the `drawtext` filter, which needs ffmpeg built with libfreetype, and plenty of real-world ffmpeg installs (a stock Homebrew build, for one) omit it. `/render-capability` greps `ffmpeg -filters` for `drawtext` and reports unavailable if it's missing, same as if `ffmpeg` weren't installed at all.

`web/app.js`'s `init()` probes `/render-capability` once (`nativeRenderAvailable`, cached for the session) and `renderVideoInWorker()` branches on it: native via `renderVideoNatively()` (a hand-rolled length-prefixed binary frame over `POST /render` — no multipart parser, matching this repo's zero-dependency convention) when available, or the original `ffmpegPool.submit(...)` WASM path otherwise. The deployed GitHub Pages build always takes the WASM branch, since there's no server there to answer the probe. Concurrent native renders (batch "Generate All") are bounded by a simple in-process queue in `server.js` (`renderLimiter`, a `makeSlotLimiter`), mirroring what `FFmpegWorkerPool` already does for WASM workers; `transcribeLimiter` is the equivalent independent queue for native Whisper transcriptions.

The `/render-progress/:id` SSE channel carries more than a bare percentage: `runNativeRender()`'s `parseProgressBlock()` accumulates each of ffmpeg's `-progress pipe:1` key=value lines (`frame`/`fps`/`speed`/`bitrate`/`out_time_ms`/...) into one object per tick, keyed off the `progress=continue`/`progress=end` line that closes each block. The `/render` handler also emits two extra phases: `{phase:"queued", activeRenders, renderSlots}` the instant the request lands (`makeSlotLimiter` exposes `getActive()` for this), and `{phase:"starting", threads, cores}` once a render slot is acquired and ffmpeg is about to spawn — distinguishing "waiting its turn" from "actually encoding", which matters when `renderLimiter`'s cap is lower than the batch size. `web/app.js`'s `describeRenderProgress()` normalizes this: the native backend's rich `{phase, pct, fps, speed, bitrate, frame, threads, ...}` object turns into a job patch, while the WASM path's bare percentage still takes the old plain-pct branch — a deliberate branch on shape, not a lossy least-common-denominator format. `updateBatchProgressStats()` splits its "how many renders are active" stat into "Encoding now" vs "Waiting for slot" (plus an "Avg. encode speed" tile) when `nativeRenderAvailable`.

Both limiters default to every CPU core (`os.cpus().length`, exposed as `cpuCount` in `/render-capability`'s response) — the render/transcribe backend is meant to use as much of the machine as the user wants. `POST /performance-settings` (body `{renderConcurrency, transcribeConcurrency}`, each clamped to `[1, cpuCount]`) lets the client adjust either limiter's cap at runtime via `setMax()`, wired to the Settings → Performance slider. Each render/transcribe subprocess also gets an explicit `-threads`/`-filter_complex_threads`/`--threads` budget (`threadBudget()` in `server.js`, `cpuCount / limiter.getMax()`) rather than leaving them unset — unset means every concurrent ffmpeg/whisper process tries to use *all* cores, so N concurrent jobs fight each other instead of sharing cleanly.

Native TTS is explicitly not part of this — Piper/Kokoro still run as WASM/ONNX in the browser either way. Native Whisper-based caption alignment (below) followed the same pattern once it was built.

### Vendored TTS assets for offline-first-launch (`main` only)

Unlike `web` (which fetches Kokoro's model/library and Piper's per-voice files from a CDN/HuggingFace at runtime), `main` vendors these locally so a fresh install works with zero network dependency:
- `web/vendor/kokoro/` — `kokoro-js@1.2.1`'s bundled `kokoro.web.js` itself, plus the ONNX-runtime WASM binaries it needs — wired via `kokoro.web.js`'s own exported `env.wasmPaths` setter, a supported override.
- `web/vendor/kokoro-model/` — the full Kokoro q8 model (`onnx/model_quantized.onnx`, ~92MB) plus config/tokenizer files and all 10 of this app's voice embeddings (`voices/*.bin`, ~522KB each — one shared model covers every voice).
- `web/vendor/piper-voices/` — just the default voice (`en_US-ryan-medium`, ~63MB); every other Piper voice still fetches from HuggingFace on first use.

`kokoro.web.js` hardcodes its model/config/tokenizer/voice fetches to a fixed HuggingFace URL prefix with no exposed config knob for that (it only re-exports a narrow `env.wasmPaths` setter, not the full transformers.js `env` object that would otherwise support `localModelPath`/`remoteHost`). `web/app.js`'s `patchKokoroFetch()` intercepts `window.fetch` for exactly that URL prefix and redirects to `web/vendor/kokoro-model/`, installed once and left active permanently (a new/already-vendored voice's `.bin` can be requested by a later `.generate()` call, not just during `from_pretrained`). Piper's `voiceProvider.fetch()` in `ensurePiper()` needed no such trick — it's this app's own code, so the default-voice case just branches to a local path directly.

### Caption-sync cascade: real alignment first, estimate last

Caption timing used to be a pure guess (`computeWordTimings` in `web/lib/captions.js` — spreads an engine's total audio duration across words proportional to a per-word weight; still exists as the final fallback). `web/app.js`'s `resolveWordTimings(text, audioBlob, durationSec, engineWordTimings)` — called from `generateSpeech()` — is the cascade, evaluated in order:

0. **Engine's own real timing** — ElevenLabs' `/with-timestamps` (character-level, via `alignWordsFromCharacters`), Browser Speech's native `boundary` events, or native Kokoro's per-token timestamps, passed as `engineWordTimings`, then realigned to the known script (see the caption-sync tier-0 alignment fix under "Native Kokoro" below) before being returned. Short-circuits everything below.
1. **Native Whisper** — mirrors the render backend's pattern: `checkWhisper()` in `server.js` checks `whisper --help` mentions `word_timestamps`, `GET /transcribe-capability`, `POST /transcribe` (raw audio bytes as the body — whisper doesn't need the known script text), `runNativeTranscribe()` shells out to `whisper <audio> --model tiny.en --word_timestamps True --output_format json --fp16 False` and flattens `segments[].words[]` (`{word, start, end, probability}`, `word` has a leading space) into `{text,start,end}`. Client-side: `probeNativeWhisperBackend()`/`nativeWhisperAvailable`, `transcribeNatively()`.
2. **VAD-corrected estimate** (the always-on default when native Whisper isn't available) — `detectSilenceGaps()` in `web/app.js` is a lightweight Web Audio energy-threshold pass (no ML model — a trained VAD's noise-robustness advantage is wasted on clean TTS output) over the decoded audio, returning real silence-run boundaries. Real inter-sentence pauses in Piper output measure ~100–140ms, not 150ms — `minSilenceWindows` reflects the measured value. `snapPausesToWords()` (`web/lib/captions.js`) nudges `computeWordTimings`' punctuation-pause guess to match a real gap when one's within tolerance, redistributing words between real anchors via the shared `distributeWordsInSpan` helper.
3. **Opt-in browser Whisper** (`#enableBrowserAsr` setting, off by default, only tried when native isn't available) — `ensureBrowserWhisper()`/`transcribeInBrowser()` mirror `ensureKokoro()`'s lazy-singleton CDN-import pattern for `@huggingface/transformers`' ASR pipeline (`Xenova/whisper-tiny.en`, `return_timestamps: "word"`).

Both Whisper tiers return the same raw shape and both feed `alignWordsBySequence()` (`web/lib/captions.js`) — an LCS-style word-sequence alignment, **not** a reuse of `alignWordsFromCharacters` (that needs an exactly reconstructable character string; Whisper's transcription can diverge from the known script — e.g. "AITAH" transcribed as "ADA", "$15,000" split into two word tokens). Matched words get real timestamps; unmatched runs interpolate between the nearest real anchors via `distributeWordsInSpan`, so a few ASR misses self-correct locally instead of reintroducing drift. Captions always show the known script's word, never Whisper's transcription. Returns `null` (never throws) on total mismatch, same fail-closed convention as `alignWordsFromCharacters`.

### Standalone app (`electron/main.js`)

`npm start` (`main` branch only) launches the same `web/` UI + `server.js` backend as a real Electron app window instead of a browser tab. There is deliberately no separate backend implementation for this: `electron/main.js`'s `startBackend()` just `require()`s `server.js`, which runs its top-level `server.listen(...)` as a side effect — identical to `node server.js`'s CLI path, just invoked from Electron's main process instead. `waitForServer()` polls briefly before `BrowserWindow.loadURL()` since the OS-level listen can take a beat after `require()` returns.

`server.js`'s `server.on("error", ...)` handler (treats `EADDRINUSE` as "another instance is already serving this" rather than crashing) exists specifically so requiring it unconditionally from Electron's main process is safe even if the app is launched twice, or launched while a standalone `node server.js` happens to already be running on the same port.

This is a first working version, not a full packaging/distribution pipeline — no per-OS installers, no code signing, no auto-update. Native rendering/transcription work identically whether the UI is a browser tab or this Electron window — same backend, same probes, same fallback logic.

### Settings: a centered tabbed modal

`#settingsPanel` is a centered modal (`width:min(1100px,92vw); height:90vh`, fade+scale transition via `.open`) with a left tab rail (`.settings-tabs`) and a scrollable content pane — each `.settings-tab-panel` is a `data-tab`-keyed section, toggled by `setSettingsTab(tab)` in `app.js` (also persists the last-open tab to `localStorage["slopdaddy_settingsTab"]`, and triggers `refreshSystemDiagnostics()`/`refreshCacheInfo()` when the Debug tab is opened). Tabs: Story, Voice, Video & Captions, Branding, Performance, Appearance, Advanced, Publish, Schedule, Debug (Publish/Schedule shown only when a local server is present).

A single global `document.addEventListener("keydown", ...)` in `init()` closes whichever overlay/modal is topmost on Escape — checked in stacking order (date/time picker → color picker → media library → debug image preview → video player → Settings itself), each branch `return`ing so one keypress closes only what's actually open. A new popup that can open on top of Settings should add its own branch here, before the `#settingsPanel` check.

Most settings thread through the existing `SETTINGS_FIELDS`/`saveSettings`/`loadSettings` mechanism (each just added to that array — no special-casing needed beyond what's noted):
- **Resolution presets** — three buttons (`applyResolutionPreset(w, h)`) that set `#resW`/`#resH` and dispatch real `input` events, so the existing auto-save and live-caption-preview listeners fire exactly as a manual edit would.
- **Encoding quality** (`#encodingQuality`, `small`/`balanced`/`high` → CRF 28/23/18 via `CRF_BY_QUALITY`) — deliberately CRF-only, not touching `-preset` (native stays `veryfast`, WASM stays `ultrafast`). Threaded as `crf` through `runJob()`'s render payload → `renderVideoNatively()`'s `meta.crf` → `server.js`'s `buildRenderArgs()` for the native path, and `msg.crf` in `ffmpeg-worker.js`'s render handler for WASM.
- **Transcribe concurrency** (`#transcribeConcurrency`) — mirrors the render-concurrency slider exactly, shown only when `nativeWhisperAvailable`.
- **Whisper model** (`#whisperModel`, `tiny.en`/`base.en`/`small.en`) — `transcribeNatively()` passes it as a `?model=` query param on `POST /transcribe`; the server validates against `WHISPER_MODELS` (defaulting to `tiny.en` if missing/invalid).
- **Theme** (`#theme`, `dark`/`light`/`system`) — a `:root[data-theme="light"]` CSS block overrides `--bg`/`--surface`/`--border`/`--text`/`--muted`/`--hover-bg`/`--hover-border`; `--accent`/`--danger`/`--green` and the primary/accent button gradients are intentionally identical in both themes (this is why a custom accent color, below, only needs one override to cover both). Applied twice: a synchronous inline `<script>` in `<head>` (before `<style>` even paints) reads `localStorage` directly and sets `document.documentElement.dataset.theme` to avoid a flash of the wrong theme on load; `applyTheme()` in `app.js` re-applies it from the live `#theme` select and wires a `matchMedia("(prefers-color-scheme: dark)")` listener for `"system"` mode, which the one-shot inline script can't do on its own. A quick top-right `#themeToggleBtn` (sun/moon icon, next to the gear) flips directly between dark/light without opening Settings; `toggleThemeQuick()` syncs `#theme`'s value to whichever concrete theme it lands on rather than touching "system", and `updateThemeToggleIcon()` (called from inside `applyTheme()` so it can't drift out of sync) shows the icon for where a click would go, not the current state.
- **Light theme shadow color** — every drop-shadow in `index.html`'s CSS is `rgba(var(--shadow-color),X)` rather than a literal `rgba(0,0,0,X)` — `--shadow-color` is an RGB triplet (no alpha, spliced directly into the `rgba()` call), pure black in dark and a soft gray-blue (`140,149,159`) in light, so every element keeps its individually-tuned alpha but light mode's shadows read as soft rather than a muddy black smudge against white. Not applied to `.media-library-tile-name`/`.media-library-tile-delete` (text-legibility overlays over thumbnail images, not shadows against the page background), `#settingsOverlay` (the modal backdrop — stays black-translucent regardless of theme), or `.cp-sv-black` (the color-picker's own HSV gradient).
- **Settings → Appearance** is its own tab (split out of Advanced) — Theme, accent color, and layout controls live there; Advanced keeps Output Folder/Settings Backup/App Updates. **Accent color** (`#accentColor`, reuses the color-picker popup built for caption colors — needs no special-casing, just the same `#<id>`/`#<id>Btn`/`#<id>Swatch`/`#<id>Label` markup shape) sets `--accent` as an inline style override on `documentElement` via `applyAccentColor()`, removed entirely when the value matches `DEFAULT_ACCENT_COLOR`. **UI text size** (`#uiFontScale`, 80–130%) scales the root font-size directly since every font-size in this file's CSS is already `rem`. **Compact layout** (`#compactMode`) and **reduce motion** (`#reduceMotion`) are `body.compact`/`body.reduce-motion` class toggles — compact tightens sidebar padding/label margins/input+button padding; reduce-motion is a blanket `* { transition: none !important; animation: none !important; }` kill switch.
- **Default output folder** (Electron only, `#outputFolder` + "Choose Folder..." button) — `electron/main.js` IPC handlers `choose-output-folder`/`save-video-file`, bridged through `electron/preload.js`. `downloadVideo(url, filename)` branches: Electron + a folder configured calls `window.electronAPI.saveVideoFile(...)`; otherwise falls through to the old `<a download>` trick.
- **Settings backup** (Export/Import/Reset, Advanced tab) — `applyLoadedSettings()` factors out the value-restoring sequence `init()` runs once, so Import doesn't duplicate it. Reset does a full `location.reload()` rather than calling `applyLoadedSettings()` in place — with `localStorage` cleared, `loadSettings()` has nothing to restore and would leave every field showing its last on-screen value instead of its real HTML-attribute default. Neither Export nor Reset touches the channel profile picture or panel-width/collapsed-state keys.
- **System diagnostics** (Debug tab) — `GET /system-info` spawns fresh `ffmpeg -version`/`ffmpeg -filters`/`whisper --help` checks on every call rather than reusing `checkFfmpeg`/`checkWhisper`'s cached booleans, so "Recheck" actually re-probes instead of reporting a server-startup-time snapshot forever.
- **Cache management** (Debug tab) — `GET /cache-info` (sums file sizes in `BG_CACHE_DIR`) and `POST /cache-clear` let a user free the background/music asset cache without a server restart.
- **Font dropdown + full color pickers** (Video & Captions tab) — `#font` is a `<select>` of web-safe names (cosmetic only: it drives the live caption *preview*'s CSS `font-family`, the actual render always burns in the one bundled `DejaVuSans.ttf`). `#textColor`/`#strokeColor` are hidden inputs driven by a shared popup (`#colorPickerPopup`, `openColorPicker(targetId, anchorEl)`): an HSV saturation/value square, hue/alpha sliders, hex + R/G/B/A fields, preset swatches. `web/lib/color.js` (`hsvToRgb`/`rgbToHsv`/`rgbToHex`/`hexToRgba`) does the math; `resolveCssColorToRgba()` (the one DOM-dependent step, needs a `<canvas>`) stays in `app.js`. Every drag/slider/field edit calls `commitColorPickerState()` immediately — Cancel is what makes this reversible, not withholding the write until Apply. Output is always `#RRGGBB`, or `#RRGGBBAA` when alpha `< 1` — matches `web/lib/ffmpeg-filters.js`'s `safeColor()` and ffmpeg's own drawtext color syntax.
- **Box Bevel** (`#boxBevel`, 0–20px, Video & Captions tab, only shown when the background box is on) — drawtext's own `box` option is a flat rectangle with no native bevel/emboss support, so `web/lib/ffmpeg-filters.js`'s `buildBevelStages()` fakes a raised edge with two extra box-only drawtext layers behind the real one: a dark copy offset toward the bottom-right and a light copy offset toward the top-left, both using the cue's own `textfile` (so their auto-sized box exactly matches the real box's dimensions) with fully transparent text. Since the real, unoffset box is drawn on top and covers the overlap, only a `boxBevel`-px sliver of each survives along two opposite edges. Threaded through both render backends (`server.js`'s `buildRenderArgs`, `ffmpeg-worker.js`'s `buildCaptionFilter`) and the live idle preview (`updateCaptionStyle()` approximates the same look with a two-tone CSS `inset` box-shadow).
- **Narration Speed** (`#videoSpeed`, 1.00–1.50x, Video Output section) — speeds up narration and captions only, audio pitch-corrected (not a naive resample); the background video always plays at its own normal, un-time-warped pace — no `setpts` appears anywhere in this codebase's video filter graphs. `web/lib/ffmpeg-filters.js`'s `buildAudioFilterChain()` applies `atempo=speed` to the raw narration input as its FIRST stage, before `adelay`/music mixing — not as a last step — so a fixed-duration title card's real-seconds delay lands in already-sped output time instead of being compressed a second time by a downstream speed change. Caption cue timing is handled entirely client-side: `runJob()` (`app.js`) divides every word's `start`/`end` by `speed` immediately after TTS returns, before any title-card word-slicing or caption-grouping reads them, so `cardDurationSec`/cue timestamps that reach the render backends are already in real/final-output time and need no filter-graph-side rescaling. Music is deliberately not sped. Verified live two ways: a synthetic background with a baked-in `drawtext` clock confirmed the frame at real output time 1.4s still reads exactly `00:00:01.400` (not time-warped) at `speed=1.3`; a real end-to-end render's total duration still shortened by the expected ratio (audio ending sooner still bounds `-shortest`, just without the video itself being compressed). `getGlobalSettings()`'s `videoSpeed` threads into both render backends' payload — but the two backends take genuinely different paths to get there: the WASM path's `renderVideoInWorker()` posts its whole payload object to the worker unchanged, so a new payload field just works, while the native path's `renderVideoNatively()` hand-builds a separate `meta` object field-by-field for its binary-frame protocol — a new payload field silently never reaches the server unless it's added to that list too (confirmed live: `speed` was correctly threaded everywhere except that one spot, producing an identical-duration output with zero effect until added there).

### No modules, no bundler — plain classic scripts sharing global scope

Everything in `web/` is loaded via `<script src="...">` tags in `index.html`, in a specific required order (later scripts call earlier ones as bare globals):
```
lib/captions.js, lib/video-utils.js, lib/job-model.js  →  worker-pool.js  →  app.js
```
`web/ffmpeg-worker.js` (a Worker, not a page script) pulls in `lib/ffmpeg-filters.js` via `importScripts()` at its own top.

The `web/lib/*.js` files use an **isomorphic module pattern**: plain top-level `function` declarations (which become globals in a classic script) plus a guarded CommonJS export at the bottom:
```js
if (typeof module !== "undefined" && module.exports) {
  module.exports = { someFunction };
}
```
This lets the exact same file work as a browser global *and* as a `require()`-able module in Node tests, with zero build step. Every file in `web/lib/` is pure (no DOM, no `fetch`, no Worker/ffmpeg globals) and has a paired `*.test.js`. When extracting logic to be testable, put pure logic in `web/lib/`, keep DOM/Worker-coupled glue code in `app.js`/`ffmpeg-worker.js`.

### Cross-origin isolation is load-bearing

`web/coi-serviceworker.js` is a service worker that injects `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy` headers on every response (GitHub Pages doesn't set these itself), which is what makes `SharedArrayBuffer` available. Both Piper's threaded ONNX runtime and ffmpeg.wasm's multi-threaded core depend on this. It also cache-first-serves the large vendored assets (`vendor/`, `onnx/`, `piper/` paths) via the Cache API, independent of the app's own `VERSION` bump cycle — app code stays network-first so version bumps propagate immediately, while multi-megabyte binaries that rarely change get cached long-term. `CACHE_NAME` in that file must be bumped by hand if the vendored asset *set* ever changes.

### Two ffmpeg.wasm cores, chosen per Worker instance

`web/vendor/ffmpeg/` (single-thread) and `web/vendor/ffmpeg/mt/` (multi-thread, needs `SharedArrayBuffer`) are both vendored. `ffmpeg-worker.js`'s `ensureLoaded()` picks one per Worker instance at load time. The multi-thread core spawns its own pthread pool sized to `navigator.hardwareConcurrency` — running several multi-thread instances at once oversubscribes the CPU badly, so `web/worker-pool.js`'s `FFmpegWorkerPool` forces every instance onto the single-thread core (`forceST`) whenever the pool size is greater than 1. A lone worker (single-video export) still prefers the multi-thread core.

### Worker pool for concurrent rendering

`FFmpegWorkerPool`/`PoolWorker` in `web/worker-pool.js` manage N independent `ffmpeg-worker.js` Worker instances (each fully self-contained). `pool.submit(taskFn)` acquires an idle worker (queueing if all are busy) and guarantees exactly one in-flight request per worker instance at a time — each `PoolWorker` owns a persistent message dispatcher rather than reassigning `onmessage` per call. `ensureFFmpeg(poolSize)` in `app.js` lazily creates/grows the shared pool; growing to a larger size destroys and replaces the old (smaller) pool rather than leaking its Workers.

### Batch page: bulk-generate screen and the manual card list are two views, not two features

The Batch tab (`#batchFlow`) is one `batchViewMode` state machine (`"setup" | "cards"`, `setBatchViewMode()`) toggling two sibling containers: `#bulkSetupView` (default), `#batchCardsView` (the original per-card list, unchanged internally — just one of two views instead of always-visible). None of `batchJobs`/rendering logic is aware of which view is showing; this is purely a display toggle.

`#bulkSetupView` is a dedicated form (count, video/music source, voice, TTS engine, caption preset, title card). Video/music each get a 3-way radio (`bulkVideoSource`/`bulkMusicSource`: `none`/`random`/`manual`). `bulkGenerateBatch()` builds one assignment plan per radio's value: `random` → `planBulkVideoAssignment()` (`web/lib/bulk-assignment.js`), `manual` → `planManualAssignment()` (cycles through the numbered picker's ordered id list), `none` → an all-`{source:"none"}` plan. `applyBulkJobDefaults()` applies the screen's voice/engine/caption/title-card selections to each newly-created job **and** syncs that card's own DOM controls to match.

"Choose for each" opens the Media Library modal in a numbered multi-select mode (`openMediaLibraryPicker({kind, max, onConfirm})`, distinct from the single-pick `openMediaLibrary(onPick, kind)`) — a CSS grid of thumbnail tiles. Clicking a tile toggles it into `mediaLibraryPickerSelection` (an ordered array — append on select, splice on deselect, re-rendering assigns each remaining tile's badge from its current array index, which renumbers the rest automatically on deselect) up to a `max` cap, with a Confirm/Cancel footer instead of closing on first click. Video thumbnails are generated lazily via `generateVideoThumbnail()` (off-DOM `<video>` seek + `<canvas>` frame grab) and cached in a session-lived `Map` keyed by item id.

`bulkGenerateBatch()` creates all `count` jobs up front, switches to `"cards"` view, and opens the full-page `#batchProgressOverlay` immediately — "Generating N stories..." while `generateIdeaAndStoryForJob()` streams every job's premise/story concurrently, each job's card re-rendered as it updates — then calls `renderAllBatch()` directly once every story is ready, reopening the same panel for the render phase ("Rendering N videos..."). No intermediate screen or extra click between generating and rendering. "Create Separately Instead" (`createBatchSeparately()`) is the only way to skip bulk generation.

### Job model: single export and batch export share one pipeline

`web/lib/job-model.js`'s `createJob()`/`resolveJobSettings()` define a "job" — one video's full state (premise/story/background/voice/style), where per-job style fields fall back to the global settings panel's values when unset. `runJob(job, globalSettings, onUpdate)` in `app.js` is the single render pipeline (transcode-if-needed → title card → TTS → render), used both by the sidebar's single-video export (a "batch of one") and by the batch composer's "Generate All". Don't fork a second render pipeline for batch-specific behavior — extend `runJob`/the job model instead.

Each phase sets `job.status` to a freeform string (`"transcode"`, `"titlecard"`, `"voice"`, `"render"`, `"done"`, `"error"`, `"cancelled"`) purely for display (`job.progressLabel || job.status`, no code branches on the specific value beyond a couple of terminal-state checks) — a new phase can introduce its own status with no other wiring needed. Title-card image generation (`renderTitleCardImage()`, pure canvas work) runs as its own sequential step before TTS, not concurrently with it as before — it's fast enough (sub-second) that losing that overlap costs nothing, and giving it a real distinct status/progress line is worth more than the few hundred ms it used to save.

Voice generation reports live progress the same way the render step already did: Kokoro's worker (`web/tts-worker.js`'s `generateKokoro`) posts `{type:"progress", current, total}` after each per-sentence synthesis chunk — a real signal, not a fake timer — threaded through `generateInWorker()`'s `onProgress` callback → `KokoroEngine.generate(text, voice, config, onProgress)` → `generateSpeech()`'s new `onGenerateProgress` 5th param → `runJob()`, which turns it into `"Generating voice... (chunk N/total)"` with a matching `progressPct`. Piper and the cloud engines never call `onProgress` (Piper has no per-call chunking of its own to report against), so their jobs keep the static `"Generating voice..."` label — this only fires for engines that actually have a real sub-step to report.

TTS engine calls go through a one-at-a-time queue (`queueTTS` in `app.js`) even when video rendering is running in parallel across the worker pool — Piper's single shared engine instance doesn't have verified concurrent-call safety, and TTS is fast enough relative to rendering that serializing it is cheap. That queue only wraps the actual `engine.generate()` call — `generateSpeech()` runs `resolveWordTimings()` (which can include a native-Whisper subprocess round trip) *after* releasing the lock, so multiple batch jobs' transcriptions run concurrently, bounded by the server's own independent `transcribeLimiter`.

The batch screen's "Parallel renders" dropdown (`#batchParallelism`) and the Settings → Performance slider (`#renderConcurrency`) both set the same server-side `renderLimiter` cap, via `applyRenderConcurrency(n)` (POSTs `/performance-settings`).

Story generation gets the same slot-limiter treatment, but purely client-side (`makeClientSlotLimiter()` in `app.js`, same shape as `server.js`'s `makeSlotLimiter`) — these are direct browser fetches to the user's own configured story provider. `storyGenLimiter` (default cap 3, `#storyGenConcurrency` in Settings → Performance) wraps every `streamChat()` call app-wide by default (not just bulk batches — unbounded concurrent requests can get silently throttled by a low-rate-limit API key, which the per-chunk stall watchdog doesn't catch since a throttled response trickles in slowly rather than erroring outright), taking effect immediately via `setMax()`, including mid-batch. One exception: `streamChat()`'s optional `skipLimiter` 4th param, used by `generateYoutubeMetadata()`'s auto-upload metadata call — a one-off per already-rendered job, not part of a bulk-generate burst, so routing it through the same queue just risks stalling an otherwise-ready-to-publish video behind unrelated jobs' story generation.

A batch job waiting behind others for its turn at `storyGenLimiter`'s cap used to be visually indistinguishable from one actively generating — both just showed "Generating story..." — which reads as "stuck" rather than "queued" once a slow provider/model (a large local Ollama model on CPU, for instance) makes that wait genuinely long; extensively verified live (real sequential Ollama calls, a real batch, a synthetic 10-call/cap-1 stress test with multi-second delays) that the limiter and orchestration were never actually hanging, just queueing exactly as designed with no visible signal that that's what was happening. `streamChat()`'s optional 5th param `onAcquired` now fires the instant a call actually starts (past `storyGenLimiter.acquire()`, not still waiting in its queue); `generateIdeaAndStoryForJob()` uses it (plus a `storyGenLimiter.getActive() >= getMax()` check before each call) to set `job.progressLabel` to "Waiting for a story slot..." vs "Generating idea..."/"Generating story..." — passed through as an `onProgress(job)` callback from `bulkGenerateBatch()` so the card re-renders on each transition.

A bulk batch sharing one background video (or music track) across many jobs doesn't re-upload identical bytes per job. `runJob()` hashes each asset (`hashAssetBytes()`, SHA-256 via Web Crypto) and calls `ensureAssetCached()`, which POSTs to `POST /cache-asset?hash=...` at most once per distinct hash for the whole session. `server.js` persists cached assets in `BG_CACHE_DIR` (`os.tmpdir()/slopdaddy-bg-cache`, wiped on every server start) keyed by hash; every job's `/render` POST references its background/music by hash and omits the raw bytes once cached — `writeAssetFile()` copies from the cache into the job's temp dir instead. `readBgFileBytes()`'s `WeakMap` cache avoids the equivalent redundant local decode for the WASM path.

`renderAllBatch()`'s "Generate All" opens a full-page dashboard overlay (`#batchProgressOverlay`) for the duration of the run — stat tiles (elapsed, ETA, CPU cores, active-renders-vs-concurrency, render backend, JS heap usage as the closest available proxy for resource use) plus a live grid of per-job cards that reuses `renderResultCard()` directly. The panel can be minimized (a floating button reopens it) without affecting the render itself.

### Reliability/UX fixes

- **Publish-panel updates reach every container showing a job, not just one.** A "done" job's card gets rendered into more than one DOM container at once — a batch run's `runJob()` progress callback calls `renderResultCard(j, grid)` (`#resultsGrid`) *and* `renderResultCard(j, progressGrid)` (`#batchProgressGrid`, the full-page batch overlay) for the same job, each producing its own separate `.publish-section` element. `maybeAutoPublish()` only fires once per job (guarded by `pub._autoUploadAttempted`), against whichever container happened to trigger it first — so the async `generatePublishMetadata()` → `generatePublishThumbnail()` → `uploadJobToYoutube()` pipeline, which used to call `renderPublishSection(job, container)` against that one closed-over reference, left every *other* live container for the same job stuck showing "Generating title/description/thumbnail from the story..." forever, even though the upload was proceeding normally in the background. `renderPublishSectionEverywhere(job)` (`querySelectorAll('.publish-section[data-job-id="..."]')`, re-renders each) replaces every post-await render call in `generatePublishMetadata`/`regeneratePublishThumbnail`/`uploadJobToYoutube` (including its upload-progress SSE handler) and `setPublishCustomThumbnail`, so a state change now reaches every visible copy of a job's publish panel, not just the one that started the pipeline.
- **Atomic YouTube store writes.** `saveYoutubeStore()` writes to `YT_STORE_PATH + ".tmp"` then `fs.renameSync()`s over the real path — an interrupted write (crash, force-quit) can no longer corrupt the file mid-save. `loadYoutubeStore()` distinguishes `ENOENT` (first run) from a real parse failure on an *existing* file (logs a warning instead of silently discarding every connected account).
- **Batch reset.** `resetBatch()`/a "New Batch" button clears `batchJobs`, `#resultsGrid`, and the progress panel.
- **API key field privacy.** `toggleKeyVisibility(id, btn)`/`copyKeyToClipboard(id, btn)` mask every key/secret field (`#apiKey`, `#ttsOpenaiKey`, `#ttsElevenlabsKey`, `#youtubeClientSecret`) by default with a Show/Hide toggle and Copy button.
- **Live idle caption preview.** `showCaptionSample()` (Settings → Video & Captions) cycles a fixed sample sentence through a `setInterval` loop for all three grouping modes (word/phrase/karaoke), driving the same real cue-builder functions real playback uses. Guarded by `if (previewActive) return;` so it doesn't clobber real playback's `subtitles`/`previewKaraokeGroups` globals if Settings is opened mid-preview — `previewActive` is set at the START of `startPreview()`, before the async TTS/caption-sync work, not after, so there's no window where a stray `showCaptionSample()` call can race in.
- **Story variety.** `STORY_CATEGORIES` (a rotating list of scenario types) + `shuffledStoryCategories()` (Fisher-Yates) feed `ideasPrompt(category)` a different scenario hint per call; `bulkGenerateBatch()` pre-shuffles one category order for the whole batch so concurrent jobs don't converge on the same premise. Ideas calls run at a higher temperature (1.05 vs. the story-writing call's 0.9).
- **Scheduling dashboard** (Settings → Schedule, shown only when `youtubeAvailable`). `allSessionJobs`/`trackJob()` track every job created this session. `refreshScheduleDashboard()` lists every job whose `publish.status === "scheduled"`, soonest-first, linking out to YouTube Studio. Deliberately display-only — no in-app "cancel a schedule" action, since that needs a `videos.update` PUT with the complete `status` resource, and an incomplete/wrong payload risks corrupting a real video's metadata with no way to verify from this environment.
- **Automatic Scheduling** (same tab, above the dashboard) — `#scheduleAutoEnabled` + a start date/time + interval (value/unit) auto-assign increasing `pub.scheduledAt` slots to auto-uploaded videos instead of leaving them to publish immediately. It's a mode of the existing Settings → Publish "auto-upload" toggle (`#youtubeAutoUpload`), not an independent trigger — enabling it also flips that toggle on if it wasn't already, since scheduling has nothing to act on otherwise. `nextScheduledSlot()` (`web/app.js`) computes each slot from a module-level `scheduleSlotCounter` that persists for the whole session (a later batch keeps extending forward rather than restarting at the configured start time and colliding with an earlier batch's still-pending slots), clamping the first slot to at least 5 minutes from now so an empty/already-elapsed start time can't produce a `publishAt` YouTube would reject. Hooked into both existing auto-upload trigger points — `maybeAutoPublish()` (fires per job as its card renders "done") and `publishAllBatch()`'s per-job `.map()` body (slots assigned synchronously before any `await`, so they land in stable array order even though the uploads then run concurrently) — always guarded by `!pub.scheduledAt` so a schedule already set manually via the per-job publish panel is never overwritten. No `server.js` changes needed: `pub.scheduledAt` flows through the exact same `runYoutubeUpload()` path (forcing `privacyStatus: "private"` + `status.publishAt`) a manual schedule already used.
- **Start-time wheel picker** — `#scheduleStartAt` is a real `<input type="datetime-local">` (so `SETTINGS_FIELDS`/`saveSettings`/`loadSettings`/`computeScheduleSlot()`'s `.value` contract is unchanged), now visually hidden behind a `#scheduleStartAtBtn` trigger button that opens `#dtPickerPopup` — an iOS-style scrolling wheel (Date/Hour/Minute/AM-PM columns) built on native CSS `scroll-snap`, not a picker library. Mirrors the color-picker popup's shell exactly (`web/app.js`'s `openColorPicker`/`closeColorPickerPopup`/`commitColorPickerState` pattern): a module-level `dtPickerState` (`null` when closed), positioned via the same clamped `getBoundingClientRect()` math, closed on outside-click via a scoped `pointerdown` listener, and live-committing every scroll-settle straight into the real backing input (dispatching a real `"input"` event) rather than deferring to Done — Cancel is what makes it reversible, Escape just closes without reverting (same as the color picker). Per-column `scroll` listeners recompute each row's fade `opacity` live from `scrollTop` distance-from-center and, debounced 150ms after scrolling settles, snap the nearest row into `dtPickerState` via `commitDtWheelSelection()`; clicking a row calls `scrollTo({behavior:"smooth"})` and lets that same debounce commit it once the animation settles. Defaults to the real current local date/time when opened with an empty backing value. `initDateTimePickerEvents()` wires the four columns' scroll listeners from `init()`, alongside `initColorPickerEvents()`.

### Story-generation providers: one registry, two wire formats

`web/lib/story-providers.js`'s `STORY_PROVIDERS` registry (mirrors `tts-engines.js`'s `TTS_ENGINES` pattern) is the single source of truth for every story-gen provider — DeepSeek, OpenAI, Groq, OpenRouter, Mistral, Google Gemini (via its OpenAI-compatibility endpoint), Anthropic, and Ollama (local, no API key, editable base URL). Adding a plain OpenAI-compatible provider is just a new registry entry (`baseUrl`, `models`, `api: "openai"`) — `app.js`'s `streamChat()` is one shared fetch+SSE-read loop for every provider, parameterized by `buildChatRequest()`/`parseSSEDelta()`. Only Anthropic's Messages API is genuinely different (separate `system` field, `x-api-key`/`anthropic-version` headers, `max_tokens` required, typed SSE events) — that's the one place both builder functions branch on `provider.api === "anthropic"`.

`populateModels()` toggles three settings-panel fields per provider's registry flags: `#modelCustomRow` when `customModel` is set (Ollama has no fixed model list), `#customBaseUrlRow` when `editableBaseUrl` is set, and `#apiKeyRow` when `needsApiKey` is false. `getApiKey()` only alerts/blocks generation for providers that declare `needsApiKey: true`.

For Ollama specifically, `refreshOllamaModelList()` (called from `populateModels()`, and from a debounced `#customBaseUrl` input listener) auto-detects installed models instead of requiring the user to type an exact name from memory — `GET <host>/api/tags` (Ollama's own native model-list API, a sibling to the `/v1` OpenAI-compatibility endpoint this app otherwise talks to for generation, derived by stripping the trailing `/v1` off `#customBaseUrl`'s value) returns the locally-pulled model list. A short 3s timeout treats "not running" as a fast, clean failure rather than leaving the Story tab feeling stuck waiting on a connection nothing answers. Populates `#ollamaModelSelect` (shown above the always-present `#modelCustom` text field, which stays the actual source of truth `getModel()` reads — selecting an option just sets its value and dispatches `input`) and preserves whatever model was already saved if it's still installed, rather than always resetting to the first detected one. This is deliberately Ollama-specific (not extended to LM Studio/vLLM, which also use the same editable-base-URL field) since `/api/tags` isn't part of the OpenAI-compatible surface those other self-hosted servers necessarily implement.

### Editable story system prompt (Settings → Story)

`storySystemPrompt()` reads `#storySystemPromptOverride`'s live value (falling back to `DEFAULT_STORY_SYSTEM_PROMPT` if empty) and always appends `"Keep it around ${wc} words."` separately — so the editable Settings textarea never contains `${...}`-style syntax a user could break while tweaking the writing-style rules. The textarea starts pre-filled with `DEFAULT_STORY_SYSTEM_PROMPT`; `resetStorySystemPrompt()` restores it.

`DEFAULT_STORY_SYSTEM_PROMPT` is loaded from `web/story-system-prompt.txt` (a plain text file, editable directly without touching JS) by `loadDefaultStorySystemPrompt()`, fetched once in `init()`'s startup `Promise.all` — before `applyLoadedSettings()` needs it to pre-fill the textarea on a fresh install. The `let` binding in `app.js` only holds a short, deliberately-not-a-duplicate one-sentence fallback string, used solely if that fetch ever fails (kept short on purpose — a single source of truth for the real prompt, not two copies that can drift apart).

### Piper/Kokoro run in a dedicated Worker, not the main thread

Piper and Kokoro's ONNX inference used to run directly on the page's main thread (`ensurePiper()`/`ensureKokoro()` in `app.js` constructed the engines in-page), which froze the entire Electron window for the full duration of every narration generation — confirmed live via a setInterval-gap probe: an unpatched build blocked the main thread for over 11 continuous seconds generating one short sentence. Neither vendored bundle exposes a way to fix this from outside: `web/vendor/kokoro/kokoro.web.js` hardcodes ORT-web's `wasm.proxy` to `false` and only re-exports a narrow `env.wasmPaths` setter; `web/vendor/piper-tts-web.js`'s `OnnxWebRuntime` keeps its ORT module in a `#private` field with no `proxy` option at all. Both engines now run inside `web/tts-worker.js`, a dedicated Worker mirroring `ffmpeg-worker.js`'s shape (classic, non-module, using dynamic `import()` for the vendored ES-module bundles) — `web/lib/tts-engines.js`'s `KokoroEngine.generate()`/`PiperEngine.generate()` are thin postMessage wrappers around `app.js`'s `generateKokoroInWorker()`/`generatePiperInWorker()` → `generateInWorker()`, which lazily spin up one persistent `ttsWorker` singleton (`ensureTtsWorker()`) and reassign `onmessage`/`onerror` per call — safe without a request-id scheme because `queueTTS` already guarantees only one TTS call is in flight app-wide at a time. The engine interface (`{audioBlob, durationSec, wordTimings?}`) is unchanged, so `generateSpeech()`/`queueTTS`/`resolveWordTimings()` needed no changes.

`ensureTtsWorker()` (`app.js`) and the worker-side `ensureKokoroEngine()`/`ensurePiperEngine()` (`web/tts-worker.js`) each cache their own load promise on first call — both now clear that cached promise in a `catch` before rethrowing on failure, so a transient Worker-startup or model-load failure doesn't permanently wedge the engine for the rest of the session; without this, every future call would just replay the same cached rejection. `generateKokoro()`'s per-chunk progress (`self.postMessage({type:"progress", ...})`) is 1-indexed (`chunkIndex + 1`) so the UI reads "chunk 1/3" while the first chunk is in flight rather than starting at "0/3".

`trimSilenceFloat32()`/`encodeMonoFloat32Wav()` (used by `generateKokoro()`'s per-chunk stitching, described below) live in `web/lib/audio-utils.js`, not inline in `tts-worker.js` — pure sample-math with no DOM/fetch/Worker coupling, so per this file's "no modules, no bundler" convention above they belong in `web/lib/` (isomorphic module pattern, paired `audio-utils.test.js`) and are pulled in via `importScripts("./lib/audio-utils.js")`.

Moving Kokoro into the worker surfaced a second, unrelated bug: `KokoroTTS.from_pretrained()` never completed inside a nested Worker — confirmed live (server access logs showed zero requests for `vendor/kokoro-model/*` even after 90+ seconds, while Piper's equivalent load in the same worker file completed in seconds). Root cause: ORT-web's threaded WASM build (the only variant vendored) spawns its own pthread-emulation sub-workers internally, and that bootstrap hangs indefinitely once nested one level deep inside another Worker, even though the identical threaded build works fine when `ffmpeg-worker.js` (a top-level worker) loads it directly. Fixed by patching `kokoro.web.js`'s exported `env` object to add a `numThreads` forwarding setter (one line, mirroring its existing `wasmPaths` setter exactly) and calling `env.numThreads = 1` before `from_pretrained()` — this skips the pthread pool entirely and runs the module single-threaded, which resolved the hang (confirmed live: from_pretrained went from never-completing to ~4s). `device: "wasm"` is also passed explicitly to `from_pretrained()`, skipping kokoro-js's own `navigator.gpu` auto-detection probe as an unrelated but unnecessary step.

### All engines but one temporarily disabled

`web/lib/tts-engines.js`'s `TTS_ENGINES_TEMP_DISABLED` greys out an engine in every `<select>` this app builds (`web/app.js`'s shared `ttsEngineOptionHtml()`, used by `buildEngineSelect()`, the bulk-batch-setup select, and the per-card batch select) with a `— disabled for now` suffix, same mechanism as the existing PocketTTS/native-Kokoro `— not installed` graying. `DEFAULT_TTS_ENGINE` tracks whichever single id is left enabled. `applyLoadedSettings()` also corrects a pre-existing saved `#ttsEngine`/`#ttsEngineQuick` value off a newly-disabled engine on load (a disabled `<option>` still accepts a direct `.value` assignment, so an old saved preference would otherwise silently stick). Nothing about any engine's implementation changed — re-enabling one is editing this array back down (or deleting it), not a re-implementation.

Currently only `kokoroNative` is enabled — browser Kokoro (`kokoro`) is parked here too, not because it's broken to use, but because of a confirmed bug: ORT-web's threaded WASM build deadlocks when its pthread pool is spawned from inside `web/tts-worker.js` (a nested `{type:"module"}` Worker never completes its handshake — see that file's `ensureKokoroEngine()` comment), forcing `numThreads=1` and making browser Kokoro slow. Native Kokoro is a Python subprocess (`server.js`'s `runNativeKokoro`) and is entirely unaffected by that browser-only bug, plus already returns real per-word timestamps — the strictly better option whenever the user has Python/`uvx` available, which is why it's the one left enabled while browser Kokoro's threading bug is unresolved.

### Per-engine TTS customization (Settings → Voice)

Each registered engine (`web/lib/tts-engines.js`'s `TTS_ENGINES`) has real tuning parameters, surfaced as per-engine rows shown/hidden by `onEngineChangeUI()`, bundled per-generation by `getEngineConfig(engineId)` into the `config` object every engine's `generate(text, voice, config)` receives:
- **Piper** — speed isn't a `generate()` argument; it's `length_scale` inside the voice's own config JSON, fed into the ONNX model's `scales` tensor. Since `PiperWebEngine.generate()` fetches the voice fresh on every call, `ensurePiper()`'s `voiceProvider.fetch` closure runs `applyPiperSpeed(json)` before returning — reads `#piperSpeed` live and sets `length_scale = (length_scale || 1) / speed` (inverse relationship).
- **Kokoro** — `KokoroEngine.generate()` passes `speed: (config && config.speed) || 1` through to kokoro-js's real `generate(text, {voice, speed})`.
- **OpenAI TTS** — request body has `model: config.model || "tts-1"` and `speed: config.speed || 1` (range 0.25–4.0).
- **ElevenLabs** — request body has `voice_settings: { stability, similarity_boost }` (both 0.0–1.0) and a selectable `model_id`.
- **Browser Speech** — `BrowserSpeechEngine.generate()` sets `utter.rate`/`utter.pitch`.

### Voice preview button

A "▶ Preview" button next to `#voice` and the sidebar's `#voiceQuick` generates a fixed short line and plays it immediately — `previewVoice(engineId, voice, btn)` calls `engine.generate(...)` directly (through `queueTTS`) rather than through `generateSpeech()`, skipping `resolveWordTimings()`'s whole caption-sync cascade — a one-off preview has no captions to sync. Plays back via a plain `new Audio(URL.createObjectURL(audioBlob))` rather than `#playerOverlay` (sized for video preview, not a quick audio blip).

### PocketTTS: a 6th engine, native backend not browser (Kyutai)

**Chatterbox** (Resemble AI) can run client-side via transformers.js/ONNX like Kokoro, but the model is 790MB–3.2GB (no offline vendoring possible) and each `generate()` call is capped around 256 tokens (~5-10s of audio), needing a chunk-and-stitch pipeline that doesn't exist in this codebase — deferred, not built.

**PocketTTS** (Kyutai, `github.com/kyutai-labs/pocket-tts`, MIT, 100M params, CPU-only) has no browser build, so it's a native backend like whisper rather than an in-browser engine: `checkPocketTts()`/`runNativePocketTts()` in `server.js` mirror `checkWhisper()`/`runNativeTranscribe()`, shelling out to `uvx pocket-tts generate --text ... --output-path ... [--language ...]` (internally chunks long text into multiple generation passes but concatenates them into one output WAV). `GET /pockettts-capability` + `POST /pockettts` (plain JSON body `{text, voice}`, unlike `/render`'s binary frame) mirror the whisper routes' shape; `pocketTtsLimiter` is a third independent `makeSlotLimiter(CPU_COUNT)`.

"Voice" for this engine is really **language** selection: `--voice` is actually a path to a custom voice-cloning reference audio file, and omitting it auto-picks one Kyutai-curated built-in voice per `--language` (english→alba, french→estelle, german→juergen, italian→giovanni, portuguese→rafael, spanish→lola). `POCKET_TTS_VOICES` exposes those 6 language ids with voice-name labels.

`buildEngineSelect()` greys out the `pocketTts` `<option>` with a "— not installed" suffix when `nativePocketTtsAvailable` is false, rather than letting it be picked and only failing on generate.

**Gotcha**: pocket-tts's WAV output writes a placeholder RIFF/`data` chunk size (a fixed ~2GB sentinel, never patched to the real size) instead of the true byte count — `parseWavDurationSec()` trusted that field and computed a wildly wrong duration (41666s for a 1.8s clip), poisoning every downstream caption timing, since a wrong-but-truthy number defeats a `parseWavDurationSec(...) || probeAudioDuration(...)` fallback. `PocketTtsEngine.generate()` skips `parseWavDurationSec` entirely and always uses `probeAudioDuration()` — the opposite tradeoff from Kokoro, a reminder that this fallback choice is genuinely per-engine.

### Native Kokoro (Python): a 7th engine, real per-word timestamps

The browser's Kokoro (kokoro-js/ONNX) never returns real word timestamps. The official Python `kokoro` package (`hexgrad/Kokoro-82M`, same model) does: its `KPipeline` exposes real per-token `start_ts`/`end_ts` on each `MToken`, derived directly from the model's own predicted durations during synthesis — not a separate ASR pass. No official CLI exists, so `server.js`'s `checkKokoroNative()`/`runNativeKokoro()`/`kokoroNativeLimiter`/`GET /kokoro-native-capability`/`POST /kokoro-native` shell out via `uvx --with kokoro --with soundfile python3 scripts/kokoro_native.py ...`. Response is JSON (`{audioBase64, durationSec, wordTimings}`), not a raw binary body, since this route needs to return both the audio and per-word metadata together. `kokoroLangForVoice()` picks KPipeline's required `lang_code` (`'a'`/`'b'`) from the voice id prefix (`af_`/`am_` vs `bf_`/`bm_`) — the browser build's kokoro-js infers this internally, but KPipeline needs it explicit. `scripts/kokoro_native.py` is bundled into the Electron package via `package.json`'s `files` (`scripts/*.py`).

`checkKokoroNative()` verifies `import kokoro, soundfile, numpy` all succeed (not just `kokoro` — the real script depends on all three, and soundfile especially needs a real `libsndfile` binary on some platforms), sharing a `KOKORO_NATIVE_WITH_ARGS` constant with `runNativeKokoro()`'s own spawn args so the dependency list can't drift between the two. `probeNativeKokoroBackend()` runs in the background rather than blocking `init()`'s startup `Promise.all` — its first-ever check can take up to 60s while `uvx` resolves kokoro's real dependencies (torch, spacy, transformers), and blocking the whole app on that would leave it non-interactive with no loading indicator. `buildEngineSelect()` re-runs once the probe settles (preserving the user's current selection around the rebuild), and `onEngineChangeUI()` also re-runs if `kokoroNative` is the active engine, so its "not available" note doesn't stick around forever once it's confirmed working.

**Packaged-app gotcha**: `checkKokoroNative()`'s probe (`python3 -c "import ..."`) never touches `scripts/kokoro_native.py`, so it passed even in a packaged build where the actual generate call failed — confirmed live: `python: can't open file '.../app.asar/scripts/kokoro_native.py': [Errno 20] Not a directory`. electron-builder's default `asar: true` packs `scripts/*.py` into the `app.asar` virtual archive, which Node's own `fs` reads transparently but an externally-spawned `python3` process can't (the OS just sees `app.asar` as a regular file). Fixed with `asarUnpack: ["scripts/*.py"]` in `package.json`'s `build` config (physically extracts it to `app.asar.unpacked/` alongside the archive) plus `runNativeKokoro()`'s `scriptPath` doing `.replace("app.asar", "app.asar.unpacked")` — a no-op in dev mode, where `__dirname` never contains `"app.asar"` at all.

`KokoroNativeEngine` reuses `KOKORO_VOICES` and is the one engine whose `generate()` actually populates `wordTimings` from real synthesis — `resolveWordTimings()`'s tier-0 short-circuit already knew how to use engine-provided timings.

**Prosody fix (Kokoro, browser build)**: the browser Kokoro engine's per-sentence-chunk concatenation used to be a raw, untrimmed splice — each chunk's own leading/trailing silence (varies chunk-to-chunk, ~40ms to 400+ms, no correlation to punctuation) stacked directly against the next chunk's, producing pauses that felt random. `trimSilenceFloat32()` trims each chunk's own near-silence first (capped at `KOKORO_MAX_TRIM_SEC`), then a fixed `KOKORO_INTER_CHUNK_GAP_SEC` (120ms) gap is inserted between chunks. Piper doesn't chunk, so this fix is Kokoro-specific.

**Caption-sync tier-0 alignment fix**: `resolveWordTimings()` used to return an engine's own real `wordTimings` completely unaligned. This was silently wrong whenever the text actually spoken differs from the known script — which happens on every AITAH/AITA story (`expandAitahForSpeech()` sends "am I the a**hole" to the engine, but captions show "AITAH") — for every engine with real timing (ElevenLabs, Browser Speech, native Kokoro). Fixed by running `engineWordTimings` through the same `alignWordsBySequence()` LCS word-matcher used for Whisper ASR mismatches, falling back to the raw untouched timings only if alignment fails outright.

### Multi-Google-Cloud-project quota (Settings → Publish)

YouTube's OAuth quota is a property of the PROJECT (the OAuth client), not the app. `youtube-accounts.json`'s `oauthClients` is a list (migrated additively from the old singular `oauthClient` on first load) — each entry is `{id, label, clientId, clientSecret, uploadLog}`, with its own independent daily-upload tracking (`recordYoutubeUpload`/`countYoutubeUploadsToday` both take an `oauthClientId`). The same real channel can be connected more than once, once per registered project (`GET/POST /youtube-oauth-clients`, `DELETE /youtube-oauth-clients/:id`) — account dedup on the OAuth callback is by `(channelId, oauthClientId)` pair, and each `account` record carries its own `oauthClientId`.

`pickAccountForUpload()` picks the requested account as-is unless its project looks to be at `YOUTUBE_QUOTA_SOFT_LIMIT` (6/day, a local heuristic) AND the same channel is also connected under a different, less-used project — in which case that connection is used instead. This check applies to the *requested* account too, not just the alternate-search fallback: an orphaned connection (its project was deleted via `DELETE /youtube-oauth-clients/:id`, which deliberately leaves referencing accounts in place) reads as "0 uploads today" from `countYoutubeUploadsToday`, so without excluding orphaned clients on the requested-account check too, a deleted-but-still-referenced connection would get returned outright before the alt search even ran. Not silent to the user: `POST /youtube-upload`'s success response includes `switchedProject`/`oauthClientLabel`, surfaced as a toast plus a persistent note under the job's publish status. The switch is exhaustion-based, not proactive round-robin: every upload targets whichever account is selected until *that one* hits the soft limit, then falls over to the next connection with headroom — it doesn't spread uploads across all connected projects from the start.

The same real channel connected under N different projects produces N separate `account` records with an identical `channelTitle` — `youtubeAccountLabel(a)` (`web/app.js`) appends `" (oauthClientLabel)"` when present, used by every account `<select>` (the per-job publish panel, the auto-upload account picker, the channel-branding-sync picker) so those connections are visually distinguishable; the connected-accounts management list already showed this via its own inline markup.

### Qwen3-TTS: investigated, not integrated

Two real PyPI packages exist under Qwen3-TTS-adjacent names: `faster-qwen3-tts` (legitimate, real GitHub-backed project) requires an NVIDIA GPU with CUDA — no CPU inference path, unlike every other native backend in this app, which target the CPU-only Homebrew-style setup this codebase assumes. The package literally named `qwen3-tts` on PyPI is an unrelated, unofficial tool that requires configuring `uv`/`pip` to trust a private third-party package index — not something to wire into a real user's machine. No safe, CPU-compatible integration path currently exists. Revisit if a CPU/GGML-backed release ships, or if Alibaba's DashScope cloud API turns out to fit the existing cloud-engine pattern.

### Captions: burned in via `drawtext`, not `subtitles`/libass

The ffmpeg.wasm build has no font *provider* (no fontconfig/CoreText/DirectWrite), so the `subtitles` filter can't render anything. Captions are burned in via `drawtext` (FreeType-direct, works with an exact bundled font file — `vendor/fonts/DejaVuSans.ttf`) instead. Each caption cue is its own `drawtext` filter instance, gated by `enable='between(t,start,end)'`, with every option set once at filter-construction time (`web/lib/ffmpeg-filters.js`'s `buildCaptionCues`/`buildDrawtextFilterChain`). There is deliberately no use of `sendcmd`/runtime filter commands — an earlier version drove a single reused `drawtext` filter via `sendcmd`, which broke captions in production twice. Keep caption rendering at filter-construction time; don't reintroduce runtime command dispatch.

### Codec support is narrow, and unsupported input is transcoded client-side first

The bundled ffmpeg.wasm core can't decode AV1/VP9/VP8 — feeding it those hangs forever with no error. `web/lib/video-utils.js`'s `detectUnsupportedCodec` sniffs the MP4 sample-entry fourcc before render; if unsupported, `autoTranscodeToH264` in `app.js` re-encodes it client-side first by seeking a `<video>` element frame-by-frame, drawing each frame to a `<canvas>`, and streaming JPEGs into the worker to be assembled with ffmpeg's own libx264 path (not `MediaRecorder`, whose H.264 *encode* support Firefox lacks).

Render calls also have a stall watchdog (`RENDER_STALL_TIMEOUT_MS` in `worker-pool.js`) — if a render produces no progress tick for 45s (typically an unsupported codec that got past sniffing), the stuck `PoolWorker`'s underlying Worker is terminated and replaced rather than leaving the UI hung.
