# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Slopdaddy generates narrated AITAH/Reddit-story videos with burned-in captions over a background clip. Piper/Kokoro TTS (client-side ONNX) for narration and a pluggable set of AI providers for story generation (see "Story-generation providers" below) always run in-browser. Rendering and caption-sync transcription both have two tiers: `server.js` shells out to the user's own installed native `ffmpeg`/`whisper` when present and capable (see "Native rendering backend" and "Caption-sync cascade" below) — falling back to ffmpeg.wasm / an in-browser estimate otherwise. No bundler, no framework either way.

**Two branches, two purposes** (as of the native-backend work): `main` is where active development happens, heading toward a standalone local app (this is that work — see "Standalone app" below). `web` is a frozen-ish snapshot kept as the zero-install "click a link" browser-only version — that's what the deployed GitHub Pages site (https://youraveragecow.github.io/Slopdaddy/) builds from, gated by `.github/workflows/pages.yml`'s `workflow_run` filter on `web`'s own `Tests` runs, not `main`'s. Backport pure-logic fixes/features to `web` when practical (cherry-pick or manual port); native-only features (this whole file's "Native rendering backend"/"Caption-sync cascade"/"Standalone app" sections) don't apply there at all, since `web`'s `server.js` stays as plain static-file serving.

## Commands

```bash
node server.js              # local dev server at http://localhost:8123 (needed for COOP/COEP headers — opening index.html via file:// breaks isolation)
npm start                    # (main branch only) launches the standalone Electron app — same UI/backend, real app window instead of a browser tab
node --test web/lib/*.test.js   # run all tests (Node's built-in test runner, zero dependencies)
node --test web/lib/foo.test.js # run a single test file
node -c web/app.js           # syntax-check a file (no linter configured — this is the closest thing)

# Dev/diagnostic tooling (main only) — see scripts/smoke-test.js
SLOPDADDY_PORT=8199 node server.js   # run a second instance without quitting a live Electron app first
SLOPDADDY_DEBUG=1 node server.js     # log real ffmpeg/whisper spawn args + per-request status/timing
npm run smoke                        # scripted round-trip check against /render, /transcribe, cache endpoints — exits non-zero on failure
npm run free-port                    # kill whatever's holding SLOPDADDY_PORT (default 8123) — mac/linux only
```

`web/` itself has no build step, no bundler, no lint config — everything there is served as-is, and `server.js`'s render/transcribe backends shell out to native `ffmpeg`/`whisper` rather than adding npm dependencies to bundle them. **`main`'s `package.json`/`package-lock.json`/`node_modules/` are new** (first-ever npm dependency in this repo's history) — `electron` only, for the standalone app wrapper; `web/` stays dependency-free regardless. Double-clicking `Open AITAH Creator Web.command` runs `node run.js`, which starts `server.js` and opens the browser for you — this still works identically on `main`, independent of the Electron app.

Tests run automatically on push/PR via `.github/workflows/test.yml` (on both `main` and `web` pushes). `.github/workflows/pages.yml` (the GitHub Pages deploy) is gated on `web`'s Tests runs specifically: it triggers via `workflow_run`, not `push` directly, and only proceeds `if` that run succeeded (or on manual `workflow_dispatch`). A red test run on `web` blocks deployment; the `github-pages` environment's deployment-branch policy was updated to allow `web` (previously only `main`).

## Architecture

### Native rendering backend (`server.js`), with automatic WASM fallback

`server.js` was originally pure static file serving. It now also exposes `POST /render` (plus `GET /render-capability` and an SSE `GET /render-progress/:id` for progress), which shells out to the user's own `ffmpeg` via `child_process` instead of ffmpeg.wasm — real native rendering is faster and doesn't hang the way the WASM multi-thread core occasionally does. It reuses `web/lib/ffmpeg-filters.js`'s pure filter-graph builders directly via `require()` (already Node-`require()`-able — that's how its own tests run) — only the exec mechanism and file I/O differ from `ffmpeg-worker.js`'s WASM path, not the actual ffmpeg invocation.

`checkFfmpeg()` in `server.js` doesn't just check that `ffmpeg` exists — captions are burned in via the `drawtext` filter, which needs ffmpeg built with libfreetype, and plenty of real-world ffmpeg installs (confirmed: a stock Homebrew build) omit it. `/render-capability` greps `ffmpeg -filters` for `drawtext` and reports unavailable if it's missing, same as if `ffmpeg` weren't installed at all.

`web/app.js`'s `init()` probes `/render-capability` once (`nativeRenderAvailable`, cached for the session) and `renderVideoInWorker()` branches on it: native via `renderVideoNatively()` (a hand-rolled length-prefixed binary frame over `POST /render` — no multipart parser, matching this repo's zero-dependency convention) when available, or the original `ffmpegPool.submit(...)` WASM path otherwise. This branch itself is silent and automatic, no user-visible difference beyond speed/reliability. The deployed GitHub Pages build always takes the WASM branch, since there's no server there to answer the probe; nothing about that build's behavior changed. Concurrent native renders (batch "Generate All") are bounded by a simple in-process queue in `server.js` (`renderLimiter`, a `makeSlotLimiter`), mirroring what `FFmpegWorkerPool` already does for WASM workers; `transcribeLimiter` is the equivalent independent queue for native Whisper transcriptions.

The `/render-progress/:id` SSE channel carries more than a bare percentage: `runNativeRender()`'s `parseProgressBlock()` accumulates each of ffmpeg's `-progress pipe:1` key=value lines (`frame`/`fps`/`speed`/`bitrate`/`out_time_ms`/...) into one object per tick, keyed off the `progress=continue`/`progress=end` line that closes each block, rather than firing on every individual line like the original bare-`out_time_ms` version did. The `/render` handler also emits two extra phases around the actual ffmpeg run: `{phase:"queued", activeRenders, renderSlots}` the instant the request lands (before `renderLimiter.acquire()` — `makeSlotLimiter` now exposes `getActive()` for this), and `{phase:"starting", threads, cores}` once a render slot is actually acquired and ffmpeg is about to spawn. This distinguishes "waiting its turn behind other jobs" from "actually encoding" — a real gap when `renderLimiter`'s cap is lower than the batch size — which the flat WASM-inherited percentage couldn't express. `web/app.js`'s `describeRenderProgress()` is the one place that normalizes this: the native backend's rich `{phase, pct, fps, speed, bitrate, frame, threads, ...}` object turns into a job patch (`renderFps`/`renderSpeed`/`renderBitrate`/`renderPhase`/a detailed `progressLabel`), while the WASM path's bare percentage number still takes the old plain-pct branch — the two backends were never going to report the same level of detail, so this is a deliberate branch on shape rather than a lossy least-common-denominator format. `updateBatchProgressStats()` (the full-page batch progress panel) also splits its "how many renders are active" stat into "Encoding now" vs "Waiting for slot" (plus an "Avg. encode speed" tile averaging `renderSpeed` across currently-encoding jobs) when `nativeRenderAvailable`, instead of one number that conflated both.

Both limiters default to every CPU core (`os.cpus().length`, exposed as `cpuCount` in `/render-capability`'s response) rather than reserving one for the OS/UI — the render/transcribe backend is meant to use as much of the machine as the user wants. `POST /performance-settings` (body `{renderConcurrency, transcribeConcurrency}`, each clamped to `[1, cpuCount]`) lets the client adjust either limiter's cap at runtime via `setMax()` — wired to the Settings -> Performance slider (`#renderConcurrency` in `web/index.html`, only shown when `nativeRenderAvailable`), which lets the user dial back if a full-throttle batch render makes the machine unresponsive. Each render/transcribe subprocess also gets an explicit `-threads`/`-filter_complex_threads`/`--threads` budget (`threadBudget()` in `server.js`, `cpuCount / limiter.getMax()`) rather than leaving them unset — unset means every concurrent ffmpeg/whisper process auto-detects and tries to use *all* cores, so N concurrent jobs fight each other instead of sharing cores cleanly.

Native TTS is explicitly not part of this — Piper/Kokoro still run as WASM/ONNX in the browser either way. Native Whisper-based caption alignment (below) followed the same pattern once it was built.

### Vendored TTS assets for offline-first-launch (`main` only)

Unlike `web` (which fetches Kokoro's model/library and Piper's per-voice files from a CDN/HuggingFace at runtime, same as ever), `main` vendors these locally so a fresh install works with zero network dependency:
- `web/vendor/kokoro/` — `kokoro-js@1.2.1`'s bundled `kokoro.web.js` itself, plus the ONNX-runtime WASM binaries (`onnx/ort-wasm-simd-threaded.jsep.{wasm,mjs}`) it needs — the latter wired via `kokoro.web.js`'s own exported `env.wasmPaths` setter, a supported override.
- `web/vendor/kokoro-model/` — the full Kokoro q8 model (`onnx/model_quantized.onnx`, ~92MB) plus `config.json`/`tokenizer.json`/`tokenizer_config.json` and all 10 of this app's voice embeddings (`voices/*.bin`, ~522KB each — one shared model covers every voice, so vendoring these ten small files is enough for all of them).
- `web/vendor/piper-voices/` — just the default voice (`en_US-ryan-medium`, ~63MB); every other Piper voice still fetches from HuggingFace on first use, unchanged.

The tricky part: `kokoro.web.js` hardcodes its model/config/tokenizer/voice fetches to `https://huggingface.co/onnx-community/Kokoro-82M-v1.0-ONNX/resolve/main/...` with no exposed config knob for that (confirmed by inspecting the bundled source — it only re-exports a narrow `env.wasmPaths` setter, not the full transformers.js `env` object that would otherwise support `localModelPath`/`remoteHost`). `web/app.js`'s `patchKokoroFetch()` narrowly intercepts `window.fetch` for exactly that URL prefix and redirects to `web/vendor/kokoro-model/`, installed once and left active permanently (a new/already-vendored voice's `.bin` can be requested by a later `.generate()` call, not just during `from_pretrained`) — everything else's fetch calls pass through untouched. Piper's `voiceProvider.fetch()` in `ensurePiper()` needed no such trick — it's this app's own code, so the default-voice case just branches to a local path directly.

Verified live (not just configured): cleared the browser's `transformers-cache`/`kokoro-voices` Cache Storage buckets first (to rule out a stale cache masking a broken redirect), then confirmed via network-request inspection that a real Kokoro generation hits only `vendor/kokoro-model/*` paths — zero requests to `huggingface.co` or `cdn.jsdelivr.net` — and same for a Piper `en_US-ryan-medium` generation hitting only `vendor/piper-voices/*`.

### Caption-sync cascade: real alignment first, estimate last

Caption timing used to be a pure guess (`computeWordTimings` in `web/lib/captions.js` — spreads an engine's total audio duration across words proportional to a per-word weight; still exists as the final fallback). `web/app.js`'s `resolveWordTimings(text, audioBlob, durationSec, engineWordTimings)` — called from `generateSpeech()` — is the cascade, evaluated in order:

0. **Engine's own real timing** — ElevenLabs' `/with-timestamps` (character-level, via `alignWordsFromCharacters`) or Browser Speech's native `boundary` events, passed straight through as `engineWordTimings` if present. Short-circuits everything below.
1. **Native Whisper** — mirrors the render backend's pattern exactly: `checkWhisper()` in `server.js` (same shape as `checkFfmpeg`, checks `whisper --help` mentions `word_timestamps` rather than just "does a binary exist"), `GET /transcribe-capability`, `POST /transcribe` (no framing needed — just raw audio bytes as the body, since whisper doesn't need the known script text), `runNativeTranscribe()` shells out to `whisper <audio> --model tiny.en --word_timestamps True --output_format json --fp16 False` and flattens `segments[].words[]` (confirmed live: `{word, start, end, probability}`, `word` has a leading space) into `{text,start,end}`. Client-side: `probeNativeWhisperBackend()`/`nativeWhisperAvailable` (probed in `init()` alongside the render probe), `transcribeNatively()`.
2. **VAD-corrected estimate** (the always-on default when native Whisper isn't available) — `detectSilenceGaps()` in `web/app.js` is a lightweight Web Audio energy-threshold pass (no ML model — confirmed via research that a trained VAD's noise-robustness advantage is wasted on clean TTS output) over the decoded audio, returning real silence-run boundaries. Threshold tuning note: real inter-sentence pauses in Piper output were measured live at ~100-140ms, not the initially-assumed 150ms — `minSilenceWindows` reflects the measured value. `snapPausesToWords()` (`web/lib/captions.js`) then nudges `computeWordTimings`' punctuation-pause guess to match a real gap when one's within tolerance, redistributing the words between real anchors via the shared `distributeWordsInSpan` helper.
3. **Opt-in browser Whisper** (`#enableBrowserAsr` setting, off by default, only tried when native isn't available) — `ensureBrowserWhisper()`/`transcribeInBrowser()` mirror `ensureKokoro()`'s lazy-singleton CDN-import pattern for `@huggingface/transformers`' ASR pipeline (`Xenova/whisper-tiny.en`, `return_timestamps: "word"`).

Both Whisper tiers (native and browser) return the same raw shape and both feed `alignWordsBySequence()` (`web/lib/captions.js`) — an LCS-style word-sequence alignment, **not** a reuse of `alignWordsFromCharacters` (that needs an exactly reconstructable character string; Whisper's transcription can diverge from the known script — confirmed live: "AITAH" transcribed as "ADA", and "$15,000" split into two separate word tokens). Matched words get real timestamps; unmatched runs interpolate between the nearest real anchors via `distributeWordsInSpan`, so a few ASR misses self-correct locally instead of reintroducing drift. Captions always show the known script's word, never Whisper's transcription. Returns `null` (never throws) on total mismatch, same fail-closed convention as `alignWordsFromCharacters`.

`SETTINGS_FIELDS`/`saveSettings`/`loadSettings` gained checkbox support (`el.type === "checkbox" ? el.checked : el.value`) for `#enableBrowserAsr` — no checkbox had ever been persisted before this.

### Standalone app (`electron/main.js`)

`npm start` (`main` branch only) launches the same `web/` UI + `server.js` backend as a real Electron app window instead of a browser tab — "Discord-style": Chromium + a Node backend, packaged as one app, not something you visit via a URL. There is deliberately no separate backend implementation for this: `electron/main.js`'s `startBackend()` just `require()`s `server.js`, which runs its top-level `server.listen(...)` as a side effect — identical to `node server.js`'s CLI path, just invoked from Electron's main process instead. `waitForServer()` polls briefly before `BrowserWindow.loadURL()` since the OS-level listen can take a beat after `require()` returns.

`server.js`'s `server.on("error", ...)` handler (treats `EADDRINUSE` as "another instance is already serving this" rather than crashing) exists specifically so requiring it unconditionally from Electron's main process is safe even if the app is launched twice, or launched while a standalone `node server.js` happens to already be running on the same port — confirmed live: a second `node server.js` invocation while the Electron app was running logged the graceful message and exited cleanly rather than crashing.

This is a first working version, not a full packaging/distribution pipeline — no `electron-builder` config, no per-OS installers, no icons, no code signing, no auto-update yet. Those are a real separate follow-up phase.

Native rendering/transcription (`server.js`'s `/render`/`/transcribe`) work identically whether the UI is a browser tab (`node server.js`) or this Electron window — same backend, same probes, same fallback logic. Nothing in `web/app.js`'s native-probe code needed to change for the Electron wrapper to work.

### Settings: a centered tabbed modal, not a right-side drawer

`#settingsPanel` used to be a 380px right-anchored slide-in drawer with one long scroll of sections. It's now a centered modal (`width:min(1100px,92vw); height:90vh`, fade+scale transition via `.open`) with a left tab rail (`.settings-tabs`) and a scrollable content pane (`.settings-content`) — each `.settings-tab-panel` is a `data-tab`-keyed section, toggled by `setSettingsTab(tab)` in `app.js` (also persists the last-open tab to `localStorage["slopdaddy_settingsTab"]`, and triggers `refreshSystemDiagnostics()`/`refreshCacheInfo()` when the Debug tab is opened). The panel's own resize-handle/`initPanelResize` wiring was removed along with it — a modal sized as a percentage of the viewport doesn't need manual width dragging the way the docked drawer did. Tabs: Story, Voice, Video & Captions, Branding, Performance, Advanced, Debug.

New settings added alongside the redesign, all threaded through the existing `SETTINGS_FIELDS`/`saveSettings`/`loadSettings` mechanism (each just added to that array — no special-casing needed beyond what's noted):
- **Resolution presets** — three buttons (`applyResolutionPreset(w, h)`) that set `#resW`/`#resH` and dispatch real `input` events, so the existing auto-save and live-caption-preview listeners fire exactly as a manual edit would.
- **Encoding quality** (`#encodingQuality`, `small`/`balanced`/`high` → CRF 28/23/18 via `CRF_BY_QUALITY`) — deliberately CRF-only, not touching `-preset` (native stays `veryfast`, WASM stays `ultrafast`, per the earlier decision to leave those alone). - **Whisper model** (`#whisperModel`, `tiny.en`/`base.en`/`small.en`) — `transcribeNatively()` passes it as a `?model=` query param on `POST /transcribe`; the server validates against `WHISPER_MODELS` (defaulting to `tiny.en` if missing/invalid) and passes it to `runNativeTranscribe()`'s `--model` flag instead of the old hardcoded value.

### No modules, no bundler — plain classic scripts sharing global scope

Everything in `web/` is loaded via `<script src="...">` tags in `index.html`, in a specific required order (later scripts call earlier ones as bare globals):
```
lib/captions.js, lib/video-utils.js, lib/job-model.js  →  worker-pool.js  →  app.js
```
`web/ffmpeg-worker.js` (a Worker, not a page script) pulls in `lib/ffmpeg-filters.js` via `importScripts()` at its own top.

The `web/lib/*.js` files use an **isomorphic module pattern**: plain top-level `function` declarations (which become globals in a classic script) plus a guarded CommonJS export at the bottom:
```js
if (typeof module !== "undefined" && module.exports) {
  module.exports = { someFunction };
}
```
This lets the exact same file work as a browser global *and* as a `require()`-able module in Node tests, with zero build step. Every file in `web/lib/` is pure (no DOM, no `fetch`, no Worker/ffmpeg globals) and has a paired `*.test.js`. When extracting logic to be testable, this is the pattern to follow — put pure logic in `web/lib/`, keep DOM/Worker-coupled glue code in `app.js`/`ffmpeg-worker.js`.

### Cross-origin isolation is load-bearing

`web/coi-serviceworker.js` is a service worker that injects `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy` headers on every response (GitHub Pages doesn't set these itself), which is what makes `SharedArrayBuffer` available. Both Piper's threaded ONNX runtime and ffmpeg.wasm's multi-threaded core depend on this. It also cache-first-serves the large vendored assets (`vendor/`, `onnx/`, `piper/` paths) via the Cache API, independent of the app's own `VERSION` bump cycle — app code (`app.js`, `index.html`, `ffmpeg-worker.js`, itself) stays network-first so version bumps propagate immediately, while multi-megabyte binaries that rarely change get cached long-term. `CACHE_NAME` in that file must be bumped by hand if the vendored asset *set* ever changes.

### Two ffmpeg.wasm cores, chosen per Worker instance

`web/vendor/ffmpeg/` (single-thread) and `web/vendor/ffmpeg/mt/` (multi-thread, needs `SharedArrayBuffer`) are both vendored. `ffmpeg-worker.js`'s `ensureLoaded()` picks one per Worker instance at load time. The multi-thread core spawns its own pthread pool sized to `navigator.hardwareConcurrency` — running several multi-thread instances at once oversubscribes the CPU badly, so `web/worker-pool.js`'s `FFmpegWorkerPool` forces every instance onto the single-thread core (`forceST`) whenever the pool size is greater than 1. A lone worker (single-video export) still prefers the multi-thread core.

### Worker pool for concurrent rendering

`FFmpegWorkerPool`/`PoolWorker` in `web/worker-pool.js` manage N independent `ffmpeg-worker.js` Worker instances (each fully self-contained — no shared state across instances). `pool.submit(taskFn)` acquires an idle worker (queueing if all are busy) and guarantees exactly one in-flight request per worker instance at a time — this is what makes concurrent rendering safe; each `PoolWorker` owns a persistent message dispatcher rather than reassigning `onmessage` per call. `ensureFFmpeg(poolSize)` in `app.js` lazily creates/grows the shared pool; growing to a larger size destroys and replaces the old (smaller) pool rather than leaking its Workers.

### Batch page: bulk-generate screen and the manual card list are two views, not two features

The Batch tab (`#batchFlow`) is one `batchViewMode` state machine (`"setup" | "cards"`, `setBatchViewMode()` in `app.js`) toggling two sibling containers in `web/index.html`: `#bulkSetupView` (default), `#batchCardsView` (the original per-card list, unchanged internally — just now one of two views instead of always-visible). None of `batchJobs`/rendering logic is aware of which view is showing; this is purely a display toggle, same idea as the existing single/batch `setFlow()`.

`#bulkSetupView` is a dedicated form (count, video/music source, voice, TTS engine, caption preset, title card) — not just the thin "count + Generate" row it used to be. Video/music each get a 3-way radio (`bulkVideoSource`/`bulkMusicSource`: `none`/`random`/`manual`) rather than a single "use random" checkbox, since "manually choose per video" needed a third option. `bulkGenerateBatch()` builds one assignment plan per radio's value: `random` → the existing `planBulkVideoAssignment()` (`web/lib/bulk-assignment.js`), `manual` → the new `planManualAssignment()` (same file — cycles through the numbered picker's ordered id list rather than randomizing), `none` → an all-`{source:"none"}` plan. `applyBulkJobDefaults()` applies the screen's voice/engine/caption/title-card selections to each newly-created job **and** syncs that card's own DOM controls to match, so "Review & Customize Each" afterward shows accurate state rather than blank overrides.

"Choose for each" (either radio) opens the Media Library modal in a new **numbered multi-select mode** (`openMediaLibraryPicker({kind, max, onConfirm})`, distinct from the existing single-pick `openMediaLibrary(onPick, kind)` used by per-card "Choose from library" links) — `renderMediaLibraryList()` branches into `renderMediaLibraryPickerGrid()`, a CSS grid of thumbnail tiles instead of the plain text list. Clicking a tile toggles it into `mediaLibraryPickerSelection` (an ordered array — append on select, splice on deselect, re-rendering assigns each remaining tile's badge from its current array index, which is what makes deselecting renumber the rest automatically) up to a `max` cap (the bulk screen's chosen story count), with a Confirm/Cancel footer instead of closing on first click. Video thumbnails are generated lazily per tile via `generateVideoThumbnail()` (off-DOM `<video>` seek + `<canvas>` frame grab, same mechanics as the codec-transcode path's frame extraction) and cached in a session-lived `Map` keyed by item id; audio items just show a fixed icon (no waveform rendering).

"Generate Stories" is not a separate step before rendering: `bulkGenerateBatch()` creates all `count` jobs up front, switches to `"cards"` view, and opens the same full-page `#batchProgressOverlay` `renderAllBatch()` uses (`openBatchProgressPanel()`) immediately — showing "Generating N stories..." while `generateIdeaAndStoryForJob()` streams every job's premise/story concurrently (`Promise.all`, each job's card re-rendered into `#batchProgressGrid` via `renderResultCard()` on every update, same as the render phase does) — safe now that each job owns its own progress card, unlike when this was sequential-only — then calls `renderAllBatch()` directly once every story is ready, which reopens the same panel fresh for the render phase ("Rendering N videos..."). No intermediate "done, now what?" screen or extra click between generating and rendering. "Create Separately Instead" (`createBatchSeparately()`) is the only way to skip bulk generation, seeding one blank card the same way `initBatchUI()` used to unconditionally (that auto-seed was removed from `initBatchUI()` — the bulk-generate screen is the default now, so nothing should assume a card already exists on first visit).

### Job model: single export and batch export share one pipeline

`web/lib/job-model.js`'s `createJob()`/`resolveJobSettings()` define a "job" — one video's full state (premise/story/background/voice/style), where per-job style fields fall back to the global settings panel's values when unset. `runJob(job, globalSettings, onUpdate)` in `app.js` is the single render pipeline (transcode-if-needed → TTS → render), used both by the sidebar's single-video export (a "batch of one") and by the batch composer's "Generate All". Don't fork a second render pipeline for batch-specific behavior — extend `runJob`/the job model instead.

TTS engine calls go through a one-at-a-time queue (`queueTTS` in `app.js`) even when video rendering is running in parallel across the worker pool — Piper's single shared engine instance doesn't have verified concurrent-call safety, and TTS is fast enough relative to rendering that serializing it is cheap. That queue only wraps the actual `engine.generate()` call, though — `generateSpeech()` runs `resolveWordTimings()` (the caption-sync cascade, which can include a real native-Whisper subprocess round trip via `/transcribe`) *after* releasing the lock, so multiple batch jobs' transcriptions run concurrently, bounded by the server's own independent `transcribeLimiter` instead of being serialized behind every other job's TTS+transcription combined.

The batch screen's "Parallel renders" dropdown (`#batchParallelism`) and the Settings → Performance slider (`#renderConcurrency`) both ultimately set the same server-side `renderLimiter` cap, via `applyRenderConcurrency(n)` in `app.js` (POSTs `/performance-settings`) — `renderAllBatch()`/`retryBatchJob()` call it with the batch dropdown's value so that control actually governs native concurrency instead of being a no-op there (`ensureRenderBackend()` only meaningfully uses its `poolSize` argument for the WASM fallback).

Story generation gets the same slot-limiter treatment, but purely client-side (`makeClientSlotLimiter()` in `app.js`, same shape as `server.js`'s `makeSlotLimiter`) rather than server-mediated — these are direct browser fetches to the user's own configured story provider, nothing to proxy through `server.js` for. `bulkGenerateBatch()` used to fire every job's ideas+story `streamChat()` calls via one unbounded `Promise.all` (up to `count * 2` concurrent requests) — a low-rate-limit API key could get throttled, and since a throttled response often trickles in slowly instead of erroring outright, `streamChat()`'s per-chunk stall watchdog (resets on every byte received, however small) never caught it: the affected job(s) would just sit on "Generating story..." far longer than the rest of the batch, intermittently and hard to reproduce since it depended on the provider's live rate-limit state. `storyGenLimiter` (default cap 3, `#storyGenConcurrency` in Settings → Performance) wraps every `streamChat()` call app-wide — not just the bulk-batch call site — so the cap holds for per-card buttons and the single-video sidebar too, even though those rarely have more than one call in flight anyway. The slider takes effect immediately via `setMax()`, including mid-batch.

A bulk batch sharing one background video (or music track) across many jobs — "same video for all", or the numbered picker cycling through fewer picks than the story count — doesn't re-upload identical bytes per job. `runJob()` hashes each asset (`hashAssetBytes()`, SHA-256 via Web Crypto) and calls `ensureAssetCached()`, which POSTs to the new `POST /cache-asset?hash=...` endpoint at most once per distinct hash for the whole session (concurrent jobs sharing a hash all await the same in-flight upload). `server.js` persists cached assets in `BG_CACHE_DIR` (`os.tmpdir()/slopdaddy-bg-cache`, wiped on every server start) keyed by hash; every job's actual `/render` POST references its background/music by hash (`bgHash`/`bgCached`, `musicHash`/`musicCached` in the request meta) and omits the raw bytes once cached — `writeAssetFile()` in `server.js` copies from the cache into the job's temp dir instead of expecting a fresh upload. `readBgFileBytes()`'s `WeakMap` cache (keyed by `File` object) avoids the equivalent redundant local decode for the WASM path, which never uploads anywhere so has nothing to hash/cache server-side.

`renderAllBatch()`'s "Generate All" opens a full-page dashboard overlay (`#batchProgressOverlay`, `openBatchProgressPanel()`/`updateBatchProgressStats()` in `app.js`) for the duration of the run — stat tiles (elapsed, ETA extrapolated from completed-count/elapsed-time throughput, CPU cores via `navigator.hardwareConcurrency`, active-renders-vs-concurrency, render backend, and `performance.memory`'s JS heap usage as the closest available proxy for "resource use" — no browser API exposes real system-wide CPU/RAM) plus a live grid of per-job cards. That grid reuses `renderResultCard()` directly rather than a separate rendering path — a finished/failed card gets the exact same Preview/Download/Retry buttons it would in `#resultsGrid`, just also mirrored into this grid. `renderResultCard()`'s batch-styling branch (title + retry button) checks for either `#resultsGrid` or `#batchProgressGrid` by id. The panel can be minimized (a floating "View Batch Progress" button reopens it) without affecting the render itself, which runs independently of whether the panel is visible.

### Reliability/UX fixes: atomic store writes, batch reset, key masking, scheduling dashboard, story variety

- **Atomic YouTube store writes.** `saveYoutubeStore()` writes to `YT_STORE_PATH + ".tmp"` then `fs.renameSync()`s over the real path — an interrupted write (crash, force-quit) can no longer corrupt the file mid-save. `loadYoutubeStore()` distinguishes `ENOENT` (first run, silently returns an empty store) from a real parse failure on an *existing* file (logs a clear warning instead of silently discarding every connected account) — the prior behavior treated both identically, which is how a corrupted file could make a real connected channel "just disappear" with zero signal.
- **Batch reset.** `resetBatch()`/a "New Batch" button clears `batchJobs`, `#resultsGrid`, and the progress panel — `cancelCurrentBatch()` previously only flipped a cancel flag, leaving old (now-orphaned) cards in place and no way to start clean without a full page reload.
- **API key field privacy.** `toggleKeyVisibility(id, btn)`/`copyKeyToClipboard(id, btn)` (shared helpers, `.key-field-row` markup) mask every key/secret field (`#apiKey`, `#ttsOpenaiKey`, `#ttsElevenlabsKey`, `#youtubeClientSecret`) by default with a Show/Hide toggle and a Copy button.
- **Live idle caption preview.** `showCaptionSample()` (Settings → Video & Captions) now actually cycles a fixed sample sentence through a `setInterval` loop for all three grouping modes (word/phrase/karaoke), driving the same real cue-builder functions (`buildWordCues`/`buildSubsFromWords`/`buildKaraokeGroups`) real playback uses — it used to show inert placeholder text for word/phrase and one frozen frame for karaoke.
- **Story variety.** `STORY_CATEGORIES` (a rotating list of scenario types) + `shuffledStoryCategories()` (Fisher-Yates) feed `ideasPrompt(category)` a different scenario hint per call; `bulkGenerateBatch()` pre-shuffles one category order for the whole batch (assigned by index before any async work starts, avoiding a race) so concurrent jobs in one batch don't all converge on the same premise. Ideas calls also run at a higher temperature (1.05 vs. the story-writing call's 0.9) to spread premises apart.
- **Scheduling dashboard** (Settings → Schedule tab, shown only when `youtubeAvailable`). `allSessionJobs`/`trackJob()` track every job created this session (single-export and batch alike — previously only batch jobs were tracked anywhere). `refreshScheduleDashboard()` lists every job whose `publish.status === "scheduled"`, soonest-first, linking out to YouTube Studio. Deliberately display-only — no in-app "cancel a schedule" action, since that needs a `videos.update` PUT with the complete `status` resource, and an incomplete/wrong payload risks silently corrupting a real video's metadata with no way to verify from this environment.

### Story-generation providers: one registry, two wire formats

`web/lib/story-providers.js`'s `STORY_PROVIDERS` registry (mirrors `tts-engines.js`'s `TTS_ENGINES` pattern) is the single source of truth for every story-gen provider — DeepSeek, OpenAI, Groq, OpenRouter, Mistral, Google Gemini (via its OpenAI-compatibility endpoint), Anthropic, and Ollama (local, no API key, editable base URL for any other self-hosted OpenAI-compatible server too). Adding a plain OpenAI-compatible provider is just a new registry entry (`baseUrl`, `models`, `api: "openai"`) — no code changes needed, since `app.js`'s `streamChat()` is one shared fetch+SSE-read loop for every provider, parameterized by `buildChatRequest()`/`parseSSEDelta()` (both pure, in `story-providers.js`, unit-tested). Only Anthropic's Messages API is genuinely different (separate `system` field instead of a `role:"system"` message, `x-api-key`/`anthropic-version` headers instead of `Bearer`, `max_tokens` required, typed SSE events) — that's the one place both builder functions branch on `provider.api === "anthropic"`; every other provider takes the default OpenAI-compatible branch.

`populateModels()` in `app.js` toggles three settings-panel fields per provider's registry flags: `#modelCustomRow` (free-text model input) when `customModel` is set (Ollama has no fixed model list), `#customBaseUrlRow` when `editableBaseUrl` is set, and `#apiKeyRow` when `needsApiKey` is false (Ollama needs no key). `getApiKey()` only alerts/blocks generation for providers that actually declare `needsApiKey: true`.

### Editable story system prompt (Settings → Story)

`storySystemPrompt()` (`app.js`) used to be a single hardcoded template literal, including a `${wc}` word-count interpolation. It's now a `DEFAULT_STORY_SYSTEM_PROMPT` constant (word-count rule removed from the body) plus a function that reads `#storySystemPromptOverride`'s live value (falling back to the constant if empty) and always appends `"Keep it around ${wc} words."` separately — this means the editable Settings textarea never contains `${...}`-style syntax a user could break while tweaking the writing-style rules. All 3 existing call sites of `storySystemPrompt()` needed zero changes — the override lookup is entirely internal to the function. The textarea starts **pre-filled** with `DEFAULT_STORY_SYSTEM_PROMPT` (not an empty box) via a first-run check in `applyLoadedSettings()`; `resetStorySystemPrompt()` restores it and dispatches an `input` event so it re-persists through the normal `SETTINGS_FIELDS` auto-save path.

### Per-engine TTS customization (Settings → Voice)

Each of the 5 registered engines (`web/lib/tts-engines.js`'s `TTS_ENGINES`) had real, previously-unexposed tuning parameters — now surfaced as per-engine rows in the Voice tab, shown/hidden by `onEngineChangeUI()` keyed off `getEngine()` (same pattern as the existing `#ttsOpenaiKeyRow`/`#ttsElevenlabsKeyRow`), and bundled per-generation by `getEngineConfig(engineId)` into the `config` object every engine's `generate(text, voice, config)` already receives:
- **Piper** — speed is *not* a `generate()` argument; it's `length_scale` inside the voice's own config JSON, fed into the ONNX model's `scales` tensor (confirmed by reading `web/vendor/piper-tts-web.js` directly). Since `PiperWebEngine.generate()` calls `voiceProvider.fetch(voice)` fresh on **every** call (not cached), `ensurePiper()`'s `voiceProvider.fetch` closure in `app.js` now runs `applyPiperSpeed(json)` before returning `[json, onnx]` — reads `#piperSpeed` live and sets `length_scale = (length_scale || 1) / speed` (inverse relationship: lower length_scale = faster). `PiperEngine.generate()` itself is untouched.
- **Kokoro** — kokoro-js's real `generate(text, {voice, speed})` already accepted `speed` (confirmed in `web/vendor/kokoro/kokoro.web.js`, default `1`, fed directly into the ONNX model) but the app never passed it. `KokoroEngine.generate()` now takes `config` and passes `speed: (config && config.speed) || 1` through.
- **OpenAI TTS** — request body gained `model: config.model || "tts-1"` (vs. `tts-1-hd`) and `speed: config.speed || 1` (API's real range is 0.25–4.0), both previously hardcoded/omitted.
- **ElevenLabs** — request body gained a `voice_settings: { stability, similarity_boost }` object (both 0.0–1.0, previously never sent — every generation used silent account defaults) and `model_id` is now selectable (`eleven_multilingual_v2`/`eleven_turbo_v2_5`/`eleven_flash_v2_5`) instead of hardcoded to multilingual_v2.
- **Browser Speech** — `BrowserSpeechEngine.generate()` gained a 3rd `config` param and now sets `utter.rate`/`utter.pitch` (standard `SpeechSynthesisUtterance` properties, previously left at their default `1`).

Every new slider/select id is a normal `SETTINGS_FIELDS` entry (free persistence via the existing mechanism), plus each range slider gets a live value-label `<span>` synced two ways: an `input` listener wired in `init()` (immediate feedback while dragging) and an explicit resync loop in `applyLoadedSettings()` (needed because `loadSettings()` restores each slider's raw `.value` without dispatching `input`, which would otherwise leave the label showing its HTML default after a restore/import).

### Voice preview button

A "▶ Preview" button next to both the Settings → Voice tab's `#voice` select and the sidebar's quick `#voiceQuick` select generates a fixed short line ("This is a preview.") and plays it immediately — `previewVoice(engineId, voice, btn)` in `app.js` calls `engine.generate(...)` directly (through `queueTTS`, same one-at-a-time lock `generateSpeech()` uses, since Piper/Kokoro's shared engine instance isn't verified concurrency-safe) rather than going through `generateSpeech()` itself, deliberately skipping `resolveWordTimings()`'s whole caption-sync cascade — a one-off preview has no captions to sync, and skipping it avoids a pointless native-Whisper round trip. Plays back via a plain `new Audio(URL.createObjectURL(audioBlob))` rather than the existing `#playerOverlay` (that's sized/styled for video preview, not a quick audio blip). `previewSettingsVoice()`/`previewQuickVoice()` are the two thin wrappers resolving which engine+voice each button's own dropdown pair currently means (the quick row falls back to the settings tab's engine/voice when its own overrides are blank, mirroring `getVoice()`'s own fallback).

### PocketTTS: a 6th engine, native backend not browser (Kyutai)

Two TTS engines were investigated for addition — only one shipped. **Chatterbox** (Resemble AI) *can* run client-side via transformers.js/ONNX like Kokoro, but the model is 790MB–3.2GB (no offline vendoring possible) and each `generate()` call is capped around 256 tokens (~5-10s of audio), needing a chunk-and-stitch pipeline that doesn't exist anywhere in this codebase — deferred, not built.

**PocketTTS** (Kyutai, `github.com/kyutai-labs/pocket-tts`, MIT, 100M params, CPU-only) has no browser build at all, so it's a native backend exactly like whisper rather than an in-browser engine: `checkPocketTts()`/`runNativePocketTts()` in `server.js` mirror `checkWhisper()`/`runNativeTranscribe()` exactly, shelling out to `uvx pocket-tts generate --text ... --output-path ... [--language ...]` (confirmed live — `uvx` downloads/caches the package in a few seconds on first run, then ~2s per generation after, including model load; internally chunks long text into multiple generation passes but transparently concatenates them into one output WAV, so callers never see the chunking). `GET /pockettts-capability` + `POST /pockettts` (plain small JSON body `{text, voice}`, unlike `/render`'s binary frame — there's no binary payload to upload) mirror the whisper routes' shape; `pocketTtsLimiter` is a third independent `makeSlotLimiter(CPU_COUNT)` alongside `renderLimiter`/`transcribeLimiter`.

"Voice" for this engine is really **language** selection, not a named-voice roster: `--voice` is actually a path to a custom voice-cloning reference audio file, and omitting it auto-picks one Kyutai-curated built-in voice per `--language` (confirmed live via `uvx pocket-tts generate --help`: english→alba, french→estelle, german→juergen, italian→giovanni, portuguese→rafael, spanish→lola) — `POCKET_TTS_VOICES` in `tts-engines.js` exposes those 6 language ids with voice-name labels, keeping the same fixed-dropdown UX as every other engine rather than building a cloning UI.

Since this is a real "probably not installed" engine for most users (unlike Piper/Kokoro's bundled models or the cloud engines' API-key gating), `buildEngineSelect()` greys out the `pocketTts` `<option>` with a "— not installed" suffix when `nativePocketTtsAvailable` is false (probed alongside the render/whisper backends in `init()`'s startup `Promise.all`), rather than letting it be picked and only failing on generate.

**Gotcha confirmed live**: pocket-tts's WAV output writes a placeholder RIFF/`data` chunk size (a fixed ~2,000,000,000-byte sentinel, never patched to the real size after writing finishes) instead of the true byte count — `parseWavDurationSec()` (`web/lib/ffmpeg-filters.js`, used by Kokoro's engine to read a WAV header directly rather than trust the DOM's own duration probe) trusted that field and computed a wildly wrong duration (41666s for a 1.8s clip) that silently poisoned every downstream caption timing, since a wrong-but-truthy number defeats a `parseWavDurationSec(...) || probeAudioDuration(...)` fallback. `PocketTtsEngine.generate()` deliberately skips `parseWavDurationSec` entirely and always uses `probeAudioDuration()` instead — the opposite tradeoff from Kokoro (whose comment explains the DOM probe undershoots specifically for *its* output), a reminder that this fallback choice is genuinely per-engine, not a one-size-fits-all default.

### Native Kokoro (Python): a 7th engine, real per-word timestamps

The browser's Kokoro (kokoro-js/ONNX) never returns real word timestamps — it always falls through to the VAD-estimate/native-Whisper caption-sync cascade. The official Python `kokoro` package (`hexgrad/Kokoro-82M`, same model) does: its `KPipeline` exposes real per-token `start_ts`/`end_ts` on each `MToken`, derived directly from the model's own predicted durations during synthesis — not a separate ASR pass, so there's nothing for the words to mismatch against. No official CLI exists for this, so `server.js`'s `checkKokoroNative()`/`runNativeKokoro()`/`kokoroNativeLimiter`/`GET /kokoro-native-capability`/`POST /kokoro-native` shell out via `uvx --with kokoro --with soundfile python3 scripts/kokoro_native.py ...` (confirmed live: real timestamps, e.g. `{"text":"Hello","start":0.275,"end":0.6}`) — same "no CLI dependency baked into the app itself" shape as PocketTTS. Response is JSON (`{audioBase64, durationSec, wordTimings}`), not a raw binary body like `/pockettts`/`/render`, since this route needs to return both the audio and per-word metadata together. `kokoroLangForVoice()` picks KPipeline's required `lang_code` (`'a'`/`'b'`) from the voice id prefix (`af_`/`am_` vs `bf_`/`bm_`) — the browser build's kokoro-js infers this internally, but KPipeline needs it explicit. `scripts/kokoro_native.py` is bundled into the Electron package via `package.json`'s `files` (`scripts/*.py`) since it's a runtime dependency, not a dev-only script like `smoke-test.js`.

`KokoroNativeEngine` in `tts-engines.js` reuses `KOKORO_VOICES` and is the one engine whose `generate()` actually populates `wordTimings` from real synthesis — `resolveWordTimings()`'s tier-0 short-circuit (see "Caption-sync cascade" above) already knew how to use engine-provided timings, but see the alignment fix noted there below.

**Prosody fix (Kokoro, browser build)**: the browser Kokoro engine's per-sentence-chunk concatenation used to be a raw, untrimmed splice — no gap insertion, but also no silence trimming, so each chunk's own leading/trailing silence (which varies chunk-to-chunk, confirmed live via energy-threshold scan: ~40ms to 400+ms with no correlation to punctuation) stacked directly against the next chunk's, producing pauses that felt random in length and placement. `trimSilenceFloat32()` in `tts-engines.js` now trims each chunk's own near-silence first (capped at `KOKORO_MAX_TRIM_SEC` so it can't eat real audio), then a single fixed `KOKORO_INTER_CHUNK_GAP_SEC` (120ms) gap is inserted between chunks — trading "however much silence the model happened to generate" for one controlled, consistent value. Piper doesn't chunk (one `generate()` call for the whole text), so this fix is Kokoro-specific; Piper's own pause variance is inherent to its ONNX/espeak phonemization, not something fixable at this layer.

**Caption-sync tier-0 alignment fix**: `resolveWordTimings()` used to return an engine's own real `wordTimings` completely unaligned — a direct passthrough. This was silently wrong whenever the text actually spoken differs from the known script, which happens on every AITAH/AITA story (`expandAitahForSpeech()` sends "am I the a**hole" to the engine, but captions are supposed to show "AITAH") — the words returned were the *spoken* tokens ("am"/"I"/"the"/...), not the known-script word, for every engine with real timing (ElevenLabs, Browser Speech, and now native Kokoro). Fixed by running `engineWordTimings` through the same `alignWordsBySequence()` LCS word-matcher already used for Whisper ASR mismatches, falling back to the raw untouched timings only if alignment fails outright. Confirmed live: native Kokoro generating "AITAH for testing..." now returns `{"text":"AITAH","start":0,"end":1.35}` (the four spoken words collapsed into the one known-script token, spanning their combined real timing) instead of leaking "am"/"I"/"the"/"a**hole" into the caption stream.

### Multi-Google-Cloud-project quota (Settings → Publish)

YouTube's OAuth quota is a property of the PROJECT (the OAuth client), not the app. `youtube-accounts.json`'s `oauthClients` is a list (migrated additively from the old singular `oauthClient` on first load, see `loadYoutubeStore()`) — each entry is `{id, label, clientId, clientSecret, uploadLog}`, with its own independent daily-upload tracking (`recordYoutubeUpload`/`countYoutubeUploadsToday` both take an `oauthClientId` now). The same real channel can be connected more than once, once per registered project (`GET/POST /youtube-oauth-clients`, `DELETE /youtube-oauth-clients/:id`) — account dedup on the OAuth callback is by `(channelId, oauthClientId)` pair, not `channelId` alone, and each `account` record carries its own `oauthClientId`. `pickAccountForUpload()` picks the requested account as-is unless its project looks to be at `YOUTUBE_QUOTA_SOFT_LIMIT` (6/day, a local heuristic) AND the same channel is also connected under a different, less-used project — in which case that connection is used instead, silently keeping "upload to channel X" working across a quota boundary. Settings UI: `#youtubeOauthClientsList` (add/remove projects) plus a `#youtubeSigninClientSelect` picker next to "Sign in with Google", since `/youtube-oauth-start` now requires an explicit `oauthClientId` (stashed alongside the PKCE verifier in `pkceChallenges`, keyed by state, so the callback knows which project's credentials to exchange the code with).

### Qwen3-TTS: investigated, not integrated

Spiked live before writing any integration code, per this repo's own "confirm the real CLI/package shape first" convention (same as PocketTTS/native-Kokoro). Two real PyPI packages exist under Qwen3-TTS-adjacent names: `faster-qwen3-tts` (legitimate, real GitHub-backed project) explicitly requires an NVIDIA GPU with CUDA — no CPU inference path at all, unlike every other native backend in this app (PocketTTS, native Kokoro, ffmpeg, whisper), which all target the CPU-only Homebrew-style setup this codebase assumes. The package literally named `qwen3-tts` on PyPI is an unrelated, unofficial tool that requires configuring `uv`/`pip` to trust a private third-party package index before it'll install — not something to wire into a real user's machine. Conclusion: no safe, CPU-compatible integration path currently exists. Revisit if a CPU/GGML-backed release ships, or if Alibaba's DashScope cloud API (unverified in this pass — would need its own live spike before integrating) turns out to fit the existing cloud-engine pattern (`STORY_PROVIDERS`-style registry entry, API-key gated).

### Captions: burned in via `drawtext`, not `subtitles`/libass

The ffmpeg.wasm build has no font *provider* (no fontconfig/CoreText/DirectWrite), so the `subtitles` filter can't render anything. Captions are burned in via `drawtext` (FreeType-direct, works with an exact bundled font file — `vendor/fonts/DejaVuSans.ttf`) instead. Each caption cue is its own `drawtext` filter instance, gated by `enable='between(t,start,end)'`, with every option set once at filter-construction time (`web/lib/ffmpeg-filters.js`'s `buildCaptionCues`/`buildDrawtextFilterChain`). There is deliberately no use of `sendcmd`/runtime filter commands anywhere in this codebase — an earlier version drove a single reused `drawtext` filter via `sendcmd`, which depended on which AVOptions ffmpeg happens to flag as runtime-settable and silently broke captions in production twice. If you're touching caption rendering, keep it at filter-construction time; don't reintroduce runtime command dispatch.

### Codec support is narrow, and unsupported input is transcoded client-side first

The bundled ffmpeg.wasm core can't decode AV1/VP9/VP8 — feeding it those hangs forever with no error. `web/lib/video-utils.js`'s `detectUnsupportedCodec` sniffs the MP4 sample-entry fourcc before render; if unsupported, `autoTranscodeToH264` in `app.js` re-encodes it client-side first by seeking a `<video>` element frame-by-frame, drawing each frame to a `<canvas>`, and streaming JPEGs into the worker to be assembled with ffmpeg's own libx264 path (not `MediaRecorder`, whose H.264 *encode* support Firefox lacks).

Render calls also have a stall watchdog (`RENDER_STALL_TIMEOUT_MS` in `worker-pool.js`) — if a render produces no progress tick for 45s (typically an unsupported codec that got past sniffing), the stuck `PoolWorker`'s underlying Worker is terminated and replaced rather than leaving the UI hung.
